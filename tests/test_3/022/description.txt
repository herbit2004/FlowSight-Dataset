## Edges, Branches & Convergence
- `req --> kv`: Represents the flow from requesting the file/data to checking the KV cache.
- `kv -- Hit --> checkComp`: If there is a cache hit, the flow proceeds to check if the data is compressed.
- `checkComp -- Yes --> decomp`: If the data is compressed, it is decompressed using Gunzip.
- `checkComp -- No --> ret1`: If the data is not compressed, it is returned directly.
- `decomp --> ret1`: The decompressed data is returned.
- `kv -- Miss --> gh`: If there is a cache miss, the data is fetched from the GitHub API.
- `gh --> checkSize`: The fetched data is checked for its size.
- `checkSize -- Yes --> skip`: If the size is greater than 2MB, caching is skipped.
- `checkSize -- No --> comp`: If the size is not greater than 2MB, the data is compressed using Gzip.
- `comp --> store`: The compressed data is stored in the KV store with a "gz:" prefix.
- `store --> ret2`: The stored data is returned.
- `skip --> ret2`: The process skips caching and returns the data.
- `ret2 --> req`: The data is returned to the request.

## Repository Context & Terminology
- **KV Cache**: A key-value cache is a data storage paradigm where data is stored and retrieved as key-value pairs. It's used for fast data retrieval.
- **GitHub API**: The GitHub API allows programmatic access to GitHub resources, such as repositories, files, and issues.
- **Gunzip**: A compression algorithm and file format used for data compression and decompression.
- **Gzip**: Another compression algorithm and file format, similar to Gunzip, used for data compression and decompression.
- **gz: prefix**: A prefix added to the key when storing compressed data in the KV store, indicating that the data is Gzip-compressed.
- **Compression**: The process of reducing the size of data to save storage space or bandwidth.
- **Caching**: The process of storing data in a cache for faster retrieval in the future.
