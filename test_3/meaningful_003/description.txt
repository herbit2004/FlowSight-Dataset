## Diagram Type & Purpose
This is a flowchart diagram illustrating the inventory deduction and rollback process within an order processing system. It outlines the steps involved in deducting inventory upon receiving an order request, handling payment success or failure, and managing inventory rollback in case of payment issues. The diagram serves as a visual representation of the workflow, aiding in understanding and troubleshooting the inventory management process.

## Edges, Branches & Convergence
- `A --> B`: An order request triggers the check for inventory availability.
- `B -- Available --> C`: If inventory is available, proceed to deduct it.
- `B -- Unavailable --> D`: If inventory is unavailable, reject the order.
- `C --> E`: After deducting inventory, log the deduction.
- `E --> F`: After logging the deduction, check if the payment was successful.
- `F -- Yes --> G`: If payment was successful, ship the order.
- `F -- No --> H`: If payment failed, rollback the inventory deduction.
- `H --> I`: Rollback involves adding the inventory back.
- `I --> J`: After adding inventory back, log the rollback.
- `J --> K`: After logging the rollback, notify the error handler.
- `C --> L`: After deducting inventory, create a deductible record.
- `L --> M`: Persist the deductible record.
- `M --> N`: Check if the deductible record was successfully persisted.
- `N -- Yes --> O`: If the record was persisted successfully, continue the workflow.
- `N -- No --> P`: If the record persistence failed, trigger a compensation transaction.
- `P --> Q`: Log the compensation trigger.
- `Q --> K`: The compensation trigger leads to notifying the error handler.
- `G --> O`: Shipping the order leads to continuing the workflow.
- `O --> R`: Continuing the workflow leads to updating the order status to processing.
- `K --> R`: Notifying the error handler leads to updating the order status to processing.
- `R --> S`: Updating the order status to processing leads to completing the order processing.

## Repository Context & Terminology
- **Inventory Deduction**: The process of reducing the quantity of a product in the inventory system when an order is placed.
- **Rollback**: Reversing a transaction or operation, typically to restore the system to a previous state. In this case, it refers to adding the deducted inventory back to the stock.
- **Compensation Transaction**: A transaction that is executed to counteract the effects of a previous transaction that failed.
- **Error Handler**: A system component responsible for managing and responding to errors that occur during the execution of a process.
- **Deductible Record**: A record indicating that inventory has been marked as deductible, usually before payment confirmation.
- **Order Status**: The current state of an order in the order processing system (e.g., "Processing", "Shipped", "Completed").
- **Workflow**: A sequence of steps or tasks that are performed to achieve a specific outcome.

## High-Density QA Ground Truth Summary
The inventory deduction and rollback process begins with receiving an order request (A), followed by checking inventory availability (B). If inventory is unavailable, the order is rejected (D). If available, the inventory is deducted (C) and logged (E). A key decision point (F) determines if payment is successful. If yes, the order is shipped (G), and the workflow continues (O) to update the order status to processing (R), eventually completing the order processing (S). If payment fails, the inventory deduction is rolled back (H), the inventory is added back (I), and the rollback is logged (J). The error handler is then notified (K), leading to updating the order status to processing (R) and completing the order processing (S). Parallel to the payment check, a deductible record is created (L) and persisted (M). If persistence fails (N), a compensation transaction is triggered (P) and logged (Q), ultimately notifying the error handler (K). The "Inventory Deduction & Rollback" subgraph encapsulates these steps, ensuring that inventory is accurately managed and any discrepancies due to payment failures or persistence issues are handled appropriately. The error handler (K) serves as a central point for managing failures and ensuring the order status is updated accordingly.
