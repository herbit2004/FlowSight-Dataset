## 图类型与用途
这是一个流程图，展示了 Manager-Orchestrator 的 8 阶段工作流程。该流程旨在自动化软件开发过程，并由多个专家（Agent）协同完成，用于概括整个系统的工作流程，如 README.md 所述。

## 图的整体布局
图采用从上到下的布局。流程从用户输入开始，经过多个阶段的处理和专家的协同工作，最终完成软件开发过程。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可以分为以下几个阶段：
- **计划与设计阶段**：包括计划制定、架构设计和数据库设计。
- **并行实现阶段**：前端和后端专家并行开发代码。
- **测试与审查阶段**：编写测试、代码审查。
- **QA反馈循环阶段**：QA测试人员进行测试，并根据缺陷情况进行修复和验证。
- **完成阶段**：生成变更日志，提交代码，并通过 Telegram 发送通知。

## 节点逐项说明
- **A (사용자 입력)**：用户输入，表示流程的起点，即用户提供的初始需求或指令。
- **B (P1: 계획 수립 Manager opus)**：第一阶段：计划制定。由 Manager 角色负责，使用 opus 模型，制定项目计划。README.md 中提到，此阶段的产出物包括 docs/plan.md 和 Tasks。
- **C (P2: 아키텍처 설계 architect-designer)**：第二阶段：架构设计。由 architect-designer 角色负责，设计项目的整体架构。README.md 中提到，此阶段的产出物包括项目结构和配置文件。
- **D (P3: DB 설계 supabase-specialist)**：第三阶段：数据库设计。由 supabase-specialist 角色负责，设计数据库结构。README.md 中提到，此阶段的产出物包括 migrations/*.sql 和 RLS。
- **E (P4: 병렬 구현)**：第四阶段：并行实现。前端和后端专家并行开发代码。README.md 中提到，此阶段的产出物是 src/** 下的代码。
- **E1 (frontend-specialist)**：前端专家，负责前端代码的实现。根据 README.md，frontend-specialist 可以修改 src/components/\*\*, src/pages/\*\*, src/hooks/\*\* 下的文件。
- **E2 (backend-specialist)**：后端专家，负责后端代码的实现。根据 README.md，backend-specialist 可以修改 src/api/\*\*, src/lib/server/\*\*, src/middleware/\*\* 下的文件。
- **F (P5: 테스트 작성 test-writer)**：第五阶段：编写测试。由 test-writer 角色负责，编写单元测试和集成测试。README.md 中提到，此阶段的产出物是 __tests__/** 下的测试文件。
- **G (P6: 코드 리뷰 code-reviewer)**：第六阶段：代码审查。由 code-reviewer 角色负责，审查代码质量和潜在问题。README.md 中提到，此阶段的产出物是评审报告。
- **H (P7: QA 피드백 루프)**：第七阶段：QA反馈循环。QA测试人员和专家参与，发现并修复缺陷。README.md 中提到，此阶段的产出物是 FINDINGS，用于自动修正缺陷。
- **H1 (CRITICAL/HIGH 있음?)**：判断是否存在严重/高优先级缺陷的决策节点。
- **H2 (Specialist 수정)**：专家修改，如果存在严重/高优先级缺陷，则由相关专家进行修复。
- **H3 (빌드 검증)**：构建验证，修复后重新构建并验证。
- **I (P8: 완료 CHANGELOG + git push + telegram)**：第八阶段：完成。生成变更日志，提交代码，并通过 Telegram 发送通知。README.md 中提到，此阶段会生成 CHANGELOG，并进行 git push 和 Telegram 通知。

## 连线、分支与汇聚关系
- `A -> B`：用户输入后，进入计划制定阶段。
- `B -> C`：计划制定完成后，传递给架构设计师进行架构设计。
- `C -> D`：架构设计完成后，传递给数据库专家进行数据库设计。
- `D -> E`：数据库设计完成后，进入并行实现阶段。
- `E -> E1`：并行实现阶段，分配给前端专家。
- `E -> E2`：并行实现阶段，分配给后端专家。
- `E1 -> F`：前端代码完成后，进入测试编写阶段。
- `E2 -> F`：后端代码完成后，进入测试编写阶段。E1 和 E2 汇聚到 F。
- `F -> G`：测试编写完成后，进入代码审查阶段。
- `G -> H`：代码审查完成后，进入 QA 反馈循环阶段。
- `H -> H1`：QA 反馈循环阶段，判断是否存在严重/高优先级缺陷。
- `H1 -- YES --> H2`：如果存在严重/高优先级缺陷，则由专家修复。
- `H2 -> H3`：专家修复后，进行构建验证。
- `H3 -> H`：构建验证后，重新进入 QA 循环。
- `H1 -- NO --> I`：如果没有严重/高优先级缺陷，则流程进入完成阶段。

## 仓库语境与术语解释
- **Manager-Orchestrator**：该系统的核心组件，负责计划、分配、验证和完成任务，但不直接编写代码，如 README.md 所述。
- **Specialist Agents**：负责具体编码和实现的专家，包括 architect-designer, frontend-specialist, backend-specialist 等，如 README.md 所述。
- **opus/sonnet**：图中 Manager 和 Specialist 使用的模型，具体细节仓库上下文未进一步说明。
- **Hooks**：用于自动强制执行策略的机制，例如 auto-validate.sh 用于 TS/ESLint 自动验证，如 README.md 所述。
- **FINDINGS**：QA 阶段的产出物，用于自动修正缺陷，如 README.md 所述。
- **Telegram**：用于发送完成通知的即时通讯软件，如 README.md 中 P8 阶段的描述。
- **git push**：将本地代码推送到远程仓库的操作，是完成阶段的一部分，如 README.md 中 P8 阶段的描述。

## 可作为 QA Ground Truth 的高信息密度摘要
该流程图描述了 Manager-Orchestrator 的 8 阶段工作流程，从用户输入开始，经过计划制定、架构设计、数据库设计等阶段，然后由前端和后端专家并行实现代码，接着进行测试和代码审查。QA 阶段会根据缺陷情况进行修复和验证，最终生成变更日志，提交代码并通过 Telegram 发送通知。其中，Manager-Orchestrator 负责协调整个流程，而 Specialist Agents 负责具体的编码和实现。Hooks 用于自动强制执行策略，保证代码质量和规范。
