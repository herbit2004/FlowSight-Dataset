- `A --> B`: User submits an order, initiating the payment check.
- `B -- Yes --> C`: Payment received, proceed to inventory check.
- `B -- No --> G`: Payment not received, send a payment reminder.
- `C --> D`: Inventory check is performed, leading to inventory availability check.
- `D -- No --> F`: Inventory not available, notify user of backorder.

## Repository Context & Terminology
- **Order**: A request from a customer to purchase goods or services. In this diagram, it represents the entire process from submission to completion.
- **Payment**: The transfer of money in exchange for goods or services. In this diagram, it's a key decision point that determines whether the order proceeds.
- **Inventory**: The stock of goods available for sale. In this diagram, it's checked for availability before packaging.
- **Backorder**: An order that cannot be fulfilled immediately due to insufficient stock. In this diagram, the user is notified of a backorder, which then leads to order completion, bypassing other steps.
- **Shipping**: The process of transporting goods from the seller to the customer. In this diagram, shipping success incorrectly leads to backorder notification.
- **Delivery**: The act of delivering the goods to the customer. In this diagram, delivery success leads to order confirmation.
- **Order Confirmation**: A notification sent to the customer confirming that their order has been processed. In this diagram, it precedes inventory update.

## High-Density QA Ground Truth Summary
The order processing workflow begins when the user submits an order (A), which immediately proceeds to a check for payment receipt (B). If payment is received (B -- Yes --> C), an inventory check is initiated; otherwise (B -- No --> G), a payment reminder is sent, looping back to the start (G --> A). If inventory is available (D -- Yes --> E), the items are packaged (E) and shipping starts (H). A successful delivery (I -- Yes --> K) triggers an order confirmation (K), followed by an inventory update (L), and finally, order completion (M). However, if delivery fails (I -- No --> J), the delivery problem is investigated (J), and shipping restarts (J --> H). Critically, shipping success (H -- Success --> F) incorrectly leads to notifying the user of a backorder (F), which then bypasses inventory update and goes directly to order completion (F --> M). Furthermore, if inventory is unavailable (D -- No --> F), the user is notified of a backorder, and the process jumps to order completion, skipping essential steps. The 'Update Inventory' step (L) happens *before* 'Order Completed' (M), which is a reversed sequence. The 'Send Payment Reminder' (G) incorrectly loops back to 'User Submits Order' (A), instead of the 'Payment Received' check (B).
