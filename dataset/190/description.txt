## 图类型与用途
这是一个流程图，描述了软件问题排查和修复的流程。它旨在帮助开发者系统性地分析问题，并采取相应的行动，最终提交修复代码的 Pull Request。

## 图的整体布局
图整体采用从上到下的布局。流程从顶部的“Issue Reported”节点开始，经过一系列判断、检查和修复步骤，最终到达底部的“Submit PR”节点。

## 分组/子图/阶段说明
图中没有显式子图/分组，但逻辑上可分为四个阶段：问题报告与重现、日志分析与调试、问题定位与测试、修复与提交。

## 节点逐项说明
- **Issue Reported**：流程的起点，表示用户或系统报告了一个问题。
- **Can Reproduce?**：一个决策节点，判断是否能够重现该问题。
- **Check Logs**：检查系统日志以获取更多关于问题的信息。
- **Request More Info**：如果无法重现问题，则需要向报告者请求更多信息。
- **Debug Level**：检查当前的调试级别。
- **Set DEBUG_LEVEL=3**：如果调试级别较低，则提高调试级别以便获取更详细的日志。根据 `hooks/config/debug.conf`，调试级别可以通过设置 `DEBUG_LEVEL` 环境变量来配置。
- **Analyze Logs**：分析日志以确定问题的根本原因。
- **Component Issue?**：一个决策节点，判断问题是否出在某个特定的组件中。
- **Run Unit Tests**：如果问题出在某个组件中，则运行该组件的单元测试。
- **Run Integration Tests**：如果问题不是组件问题，则运行集成测试。
- **Check System State**：检查系统的整体状态，例如资源使用情况、网络连接等。
- **Check Configuration**：检查系统的配置是否正确。
- **Fix Component**：修复导致问题的组件代码。
- **Test Fix**：测试修复后的代码，确保问题已解决。
- **Submit PR**：提交包含修复的代码的 Pull Request。

## 连线、分支与汇聚关系
- `Start -> Reproduce`：从 "Issue Reported" 开始，进入 "Can Reproduce?" 的判断。
- `Reproduce -- Yes --> Logs`：如果可以重现，则检查 "Check Logs"。
- `Reproduce -- No --> More`：如果无法重现，则 "Request More Info"。
- `Logs -> Level`：检查日志后，进入 "Debug Level" 的判断。
- `Level -- Low --> Increase`：如果调试级别较低，则 "Set DEBUG_LEVEL=3"。
- `Level -- High --> Analyze`：如果调试级别较高，则 "Analyze Logs"。
- `Increase -> Reproduce`：提高调试级别后，回到 "Can Reproduce?" 重新开始。
- `Analyze -> Component`：分析日志后，进入 "Component Issue?" 的判断。
- `Component -- Yes --> Unit`：如果是组件问题，则 "Run Unit Tests"。
- `Component -- No --> Integration`：如果不是组件问题，则 "Run Integration Tests"。
- `Unit -> Fix`：运行单元测试后，"Fix Component"。
- `Integration -> System`：运行集成测试后，"Check System State"。
- `System -> Config`：检查系统状态后，"Check Configuration"。
- `Config -> Fix`：检查配置后，"Fix Component"，形成汇聚关系。
- `Fix -> Test`：修复组件后，"Test Fix"。
- `Test -> PR`：测试修复后，"Submit PR"。
- `More -> Start`：请求更多信息后，回到 "Issue Reported" 重新开始。

## 仓库语境与术语解释
- **Issue Reported**：表示在代码仓库中发现了一个需要修复的问题。
- **Debug Level**：调试级别，用于控制日志输出的详细程度。可以在 `hooks/config/debug.conf` 中配置 `DEBUG_LEVEL`。
- **Component**：代码仓库中的一个模块或组件。
- **Unit Tests**：针对代码仓库中特定组件的测试。
- **Integration Tests**：测试代码仓库中不同组件之间交互的测试。
- **PR (Pull Request)**：一种代码提交方式，用于将修复后的代码合并到主分支。
- **hooks/config/debug.conf**：该文件用于配置 Claude-Gemini Bridge 的调试级别和其他参数。
- **test/test-runner.sh**：该脚本用于运行 Claude-Gemini Bridge 的自动化测试。

## 可作为 QA Ground Truth 的高信息密度摘要
该流程图描述了从问题报告到提交修复代码的完整流程。流程从“Issue Reported”开始，首先判断问题是否可以重现，如果可以，则检查日志并根据调试级别进行分析；如果无法重现，则请求更多信息。通过日志分析确定问题是否是组件问题，然后分别运行单元测试或集成测试。最终，修复组件并测试修复，最后提交 Pull Request。其中，调试级别的设置和组件问题的判断是两个关键分支。该流程旨在帮助开发者系统性地解决代码仓库中的问题。
