## Diagram Type & Purpose
This is a flowchart diagram illustrating the process flow of an order processing system. It depicts the steps involved from when a user submits an order to when the order is completed, including inventory checks, payment processing, shipping, and handling of potential issues. The diagram serves as a visual representation of the order fulfillment workflow.

## Overall Layout
The diagram's layout is top-down (TD). It starts with the "User Submits Order" node at the top and flows downwards through various processes and decision points. The diagram concludes with "Notify User of Delay", "File Complaint", and "Update Inventory" nodes.

## Edges, Branches & Convergence
- `A --> B`: User submits an order, initiating the inventory check.
- `B -- No --> C`: If inventory is not available, the user is notified of a delay.
- `B -- Yes --> D`: If inventory is available, payment processing begins.
- `D -- Success --> E`: Successful payment processing leads to shipping label creation.
- `D -- Failure --> A`: Failed payment processing loops back to the "User Submits Order" node.
- `E --> F`: A shipping label is created, leading to a check for package arrival.
- `F -- Yes --> G`: If the package has arrived, the order is marked as completed.
- `F -- No --> H`: If the package has not arrived, an order confirmation is sent.
- `H --> I`: Sending order confirmation leads to filing a complaint.
- `I --> D`: Filing a complaint loops back to payment processing.
- `G --> J`: Order completion triggers inventory update.
- `J --> C`: Inventory update leads to notifying the user of a delay.

## High-Density QA Ground Truth Summary
The order processing flowchart begins with the "User Submits Order" node, which initiates an "Inventory Available?" check. If inventory is unavailable ("No" branch), the user is notified of a delay. If inventory is available ("Yes" branch), the system proceeds to "Payment Processed". A failed payment loops back to "User Submits Order". Upon successful payment, a "Shipping Label Created". Next, the system checks "Package Arrived?". If "Yes", the "Order Completed" node is reached, triggering "Update Inventory", which then incorrectly leads to "Notify User of Delay". If the package has not arrived ("No" branch), an "Send Order Confirmation" is sent, which then leads to "File Complaint", which then loops back to "Payment Processed". The end nodes are "Notify User of Delay", "File Complaint", and "Update Inventory". The illogical flow of sending an order confirmation *after* the package is expected to have arrived, and the subsequent filing of a complaint looping back to payment processing, highlight the diagram's counterfactual nature.
