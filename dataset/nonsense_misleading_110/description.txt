## Diagram Type & Purpose
This is a flowchart diagram depicting the order processing workflow of an e-commerce system. It illustrates the sequence of steps involved from when a user submits an order to when the order is completed or a refund is issued. The diagram serves as a visual representation of the business logic and processes governing order fulfillment and customer service.

## Overall Layout
The diagram has a top-down (TD) layout. The flow starts at the top with "User Submits Order" and progresses downwards through a series of decision points and actions, eventually leading to the "End" node at the bottom. There is a feedback loop from late payment reminders back to the start.

## Subgraphs / Stages
No explicit subgraphs; logically divided into 6 stages: Order Submission & Payment, Inventory & Shipping, Feedback Collection, Order Closure, Refund Processing, and Order Completion.

## Edges, Branches & Convergence
- `A --> B`: User submits an order, initiating the order processing workflow.
- `B -- Yes --> C`: Payment received, proceed to inventory check.
- `B -- No --> Z`: Payment not received, send a late payment reminder.
- `Z --> A`: After sending the late payment reminder, the flow loops back to the beginning, "User Submits Order".
- `C --> D`: Inventory check is performed.
- `D -- Yes --> E`: Inventory is available, generate shipping label.
- `D -- No --> F`: Inventory is not available, notify user of delay.
- `F --> A`: After notifying the user of delay, the flow loops back to the beginning, "User Submits Order".

- `G --> H`: Order packaged, ship the order.
- `H --> I`: Order shipped, update inventory.

- `L --> M`: Feedback request forwarded, check if feedback received.
- `M -- No --> N`: Feedback not received, close order.
- `M -- Yes --> O`: Feedback received, process feedback.

- `R --> V`: Order history reviewed, end.

## Repository Context & Terminology
- **User Submits Order**: Standard meaning is a customer placing an order. In this diagram, it's the starting point and also the point where the process loops back to after a late payment reminder or a delay notification, implying the user needs to resubmit the order.
- **Payment Received?**: Standard meaning is checking if payment has been successfully processed. In this diagram, if payment is not received, the process loops back to the beginning, suggesting a resubmission of the order is required.
- **Inventory Check**: Standard meaning is verifying if items are in stock. In this diagram, if inventory is unavailable, the user is notified of a delay, and the process loops back to the beginning.
- **Shipping Confirmation Sent?**: Standard meaning is confirming that the order has been shipped. In this diagram, if the confirmation is not sent, a shipping error is logged, and the process loops back to "Ship Order", which is illogical.
- **Feedback Request**: Standard meaning is soliciting feedback from the customer. In this diagram, feedback is requested after shipping confirmation.
- **Refund Requested?**: Standard meaning is checking if the customer has requested a refund. In this diagram, this check occurs after archiving the order data, which is an unusual sequence.
- **Refund Approved?**: Standard meaning is determining if the refund request is valid. In this diagram, if the refund is not approved, the user is notified of a delay, which is incorrect; it should be a refund denial.

## High-Density QA Ground Truth Summary
The order processing workflow begins when the "User Submits Order," which then proceeds to check if "Payment Received?". If payment is not received, a "Send Late Payment Reminder" is triggered, looping back to the "User Submits Order." If payment is received, an "Inventory Check" is performed. If "Inventory Available?", the process moves to "Generate Shipping Label"; otherwise, the "Notify User of Delay" step is activated, also looping back to the "User Submits Order." After generating the shipping label, the order is "Package Order", then "Ship Order", and "Update Inventory". Next, it checks "Shipping Confirmation Sent?". If not, a "Log Shipping Error" is recorded, looping back to "Ship Order". If shipping confirmation is sent, a "Forward Feedback Request" is sent, and the system checks "Feedback Received?". If not, the "Close Order" step is executed; otherwise, "Process Feedback" is performed before closing the order. The "Archive Order Data" step follows, and then the system checks "Refund Requested?". If not, the "Review Order History" step is performed, leading to the "End" node. If a refund is requested, the "Process Refund Request" step is initiated, followed by "Refund Approved?". If approved, "Issue Refund" is executed, then "Review Order History" and "End". If the refund is not approved, the "Notify User of Delay" step is triggered, which is an error, as it should be a refund denial. The diagram contains several illogical loops and reversed sequences, such as updating inventory before shipping confirmation and looping back to ship order after logging a shipping error.
