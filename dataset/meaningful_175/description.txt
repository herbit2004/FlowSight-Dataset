## Diagram Type & Purpose
This is a flowchart diagram illustrating the workflow of an order review system. It depicts the process from initial order event to final reporting and feedback, including sampling, review, and escalation steps. The diagram serves as a visual representation of the system's logic and data flow.

## Overall Layout
The diagram flows from top to bottom (TB). It is hierarchically structured into four subgraphs representing different stages of the order review process. The start node is "Order System Event" and the end nodes are "Order System", "Error Logging", and "Dashboard Updates".

## Subgraphs / Stages
The diagram contains four subgraphs:
- **Data Acquisition Layer**: Handles initial order events and acceptance.
- **Sampling & Assignment**: Determines if an order meets sampling criteria and assigns review tasks.
- **Review & Analysis**: Manages the review process, including task claiming, form population, and review submission.
- **Reporting & Feedback**: Updates order status, calculates review scores, and provides feedback through dashboards and error logging.

## Edges, Branches & Convergence
- `A --> B`: Order system event is published to the Kafka topic.
- `B --> C`: Order event is processed to determine if the order is accepted.
- `C -- Yes --> D`: If the order is accepted, it is sent to the Sampling Service API.
- `C -- No --> E`: If the order is not accepted, it is rejected and an error is logged.
- `D --> F`: The order is checked against sampling criteria.
- `F -- Yes --> G`: If the sampling criteria are met, a review task is created.
- `F -- No --> H`: If the sampling criteria are not met, the review is skipped.
- `G --> I`: The review task is added to the task queue.
- `H --> I`: The process skips to the task queue.
- `I --> J`: Review tasks are retrieved via the Review Task API.
- `J --> K`: A reviewer attempts to claim a task.
- `K -- Yes --> L`: If a reviewer claims the task, a review form is populated.
- `K -- No --> I`: If no reviewer claims the task, the process returns to the task queue.
- `L --> M`: The reviewer provides input.
- `M --> N`: The review is submitted.
- `N --> O`: The review is checked against pass/fail criteria.
- `O -- Pass --> P`: If the review passes, it is reported as passed.
- `O -- Fail --> Q`: If the review fails, an escalation is initiated.
- `Q --> R`: The escalation workflow is executed.
- `P --> S`: The order status is updated.
- `R --> S`: The order status is updated after escalation.
- `S --> T`: The updated order status is published to the Kafka topic.
- `T --> U`: The order system is updated.
- `E --> V`: Errors are logged.
- `N --> W`: The review score is calculated.
- `W --> X`: The review is stored in the review database.
- `X --> Y`: Dashboards are updated.

## Repository Context & Terminology
- **Kafka Topic**: A category or feed name to which records are published in Kafka, a distributed event streaming platform.
- **API (Application Programming Interface)**: A set of defined rules that enable different applications to communicate with each other.
- **Task Queue**: A queue that distributes units of work as tasks among multiple workers or systems.
- **Review DB**: A database specifically designed to store and manage review data.
- **Sampling Service**: A service responsible for selecting a subset of orders for review based on predefined criteria.
- **Escalation Workflow**: A defined process for handling reviews that fail to meet certain criteria, often involving higher-level review or intervention.
- **Dashboard**: A visual display of key performance indicators (KPIs) and other relevant metrics.

## High-Density QA Ground Truth Summary
The order review process begins with an "Order System Event" which is then published to a "Kafka Topic: order.events". The system then checks if the "Order Accepted?". If 'No', the process ends with "Reject, Log Error". If 'Yes', the process proceeds to "Sampling Service API" to determine if the order "Met sampling criteria?". If 'Yes', a "Create Review Task" is triggered; if 'No', the review is "Skip Review". Both paths converge at the "Task Queue: Review Assignments". A "Review Task API" allows reviewers to claim tasks; if "Reviewer Claims Task" is 'No', the process loops back to the "Task Queue". If 'Yes', a "Populate Review Form" step is initiated, followed by "Reviewer Input" and "Submit Review". The system then checks if "Pass/Fail Criteria Met?". If 'Pass', a "Report: Review Passed" is generated; if 'Fail', an "Initiate Escalation" and "Escalation Workflow" are triggered. Both paths converge at "Update Order Status", which publishes to "Kafka Topic: order.updates" before updating the "Order System". Concurrently, the "Submit Review" step triggers "Review Score Calculation" and "Store in Review DB", which updates "Dashboard Updates". The Kafka topics serve as message queues, enabling asynchronous communication between different components of the order review system.
