## 图类型与用途
这是一个流程图，描述了 Django + React + TypeScript 应用的持续集成/持续部署 (CI/CD) 流程。它在仓库中的作用是展示从代码变更到应用上线的自动化流程，对应 README 中 "Virtualized Deploy Workflow" 和 "Bare-metal Deploy Workflow" 的概括。

## 图的整体布局
图整体采用从左到右的布局。从开发者修改代码开始，经过一系列构建、测试、发布和部署步骤，最终应用更新上线或流水线取消。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可以分成四个阶段：代码变更与构建、Docker 镜像处理、部署准备、应用更新与监控。

## 节点逐项说明
- **Make changes to the application**：表示开发者对应用程序进行修改，作为整个流程的起点。
- **Build and test frontend and backend**：表示构建和测试前端（React）和后端（Django）代码。对应 `.github/workflows/build-and-test.yml` 中的 `build-frontend` 和 `build-backend` jobs。
- **Success?**：一个判断节点，检查构建和测试是否成功。
- **Build and test docker image**：表示构建和测试 Docker 镜像。
- **Success?**：一个判断节点，检查 Docker 镜像构建和测试是否成功。
- **Publish docker image to GitHub packages**：表示将 Docker 镜像发布到 GitHub Packages。对应 `.github/workflows/docker-publish.yml`。
- **Success?**：一个判断节点，检查 Docker 镜像发布是否成功。
- **Deploy**：代表部署阶段。
- **Login into VM and copy docker compose file from repo**：代表登录到虚拟机 (VM) 并从代码仓库复制 Docker Compose 文件。
- **Success?**：一个判断节点，检查 Docker Compose 文件复制是否成功。
- **Pull previously pushed Docker image and execute most recent docker compose file**：代表拉取之前推送的 Docker 镜像并执行最新的 Docker Compose 文件。
- **Success?**：一个判断节点，检查 Docker Compose 文件执行是否成功。
- **Updates are live**：代表更新已上线，部署完成。
- **Cancel pipeline**：代表取消流水线，通常是因为构建、测试或发布失败。
- **Better check your system's health**：代表建议检查系统健康状况，通常是因为部署失败。

- `Make changes to the application -- Commit --> Build and test frontend and backend`：开发者提交代码后触发构建和测试流程。

- `Success? -- No --> Cancel pipeline`：如果构建和测试失败，则取消流水线。
- `Build and test docker image --> Success?`：Docker 镜像构建和测试完成后，进入成功判断。

- `Success? -- No --> Cancel pipeline`：如果 Docker 镜像构建和测试失败，则取消流水线。
- `Publish docker image to GitHub packages --> Success?`：Docker 镜像发布完成后，进入成功判断。
- `Success? -- Yes --> Deploy`：如果 Docker 镜像发布成功，则进入部署阶段。
- `Success? -- No --> Cancel pipeline`：如果 Docker 镜像发布失败，则取消流水线。
- `Deploy --> Login into VM and copy docker compose file from repo`：在部署阶段，登录到虚拟机并复制 Docker Compose 文件。
- `Login into VM and copy docker compose file from repo --> Success?`：Docker Compose 文件复制完成后，进入成功判断。
- `Success? -- Yes --> Pull previously pushed Docker image and execute most recent docker compose file`：如果 Docker Compose 文件复制成功，则拉取 Docker 镜像并执行 Docker Compose 文件。
- `Success? -- No --> Cancel pipeline`：如果 Docker Compose 文件复制失败，则取消流水线。
- `Pull previously pushed Docker image and execute most recent docker compose file --> Success?`：Docker Compose 文件执行完成后，进入成功判断。
- `Success? -- Yes --> Updates are live`：如果 Docker Compose 文件执行成功，则更新上线。
- `Success? -- No --> Better check your system's health`：如果 Docker Compose 文件执行失败，则建议检查系统健康状况。
- `Build and test frontend and backend -- No --> Cancel pipeline`：形成汇聚关系。
- `Build and test docker image -- No --> Cancel pipeline`：形成汇聚关系。
- `Publish docker image to GitHub packages -- No --> Cancel pipeline`：形成汇聚关系。
- `Login into VM and copy docker compose file from repo -- No --> Cancel pipeline`：形成汇聚关系。

## 仓库语境与术语解释
- **GitHub Actions**: 仓库使用 GitHub Actions 进行 CI/CD，相关配置文件位于 `.github/workflows/` 目录下，例如 `deploy-vm.yml` 和 `deploy-bare-metal.yml`。
- **Docker**: 仓库使用 Docker 进行应用容器化，`Dockerfile` 定义了 Docker 镜像的构建过程。
- **Docker Compose**: 仓库使用 Docker Compose 管理多容器应用，`docker-compose.yml` 定义了应用的各个服务及其依赖关系。
- **Poetry**: 仓库使用 Poetry 管理 Python 依赖，`pyproject.toml` 和 `poetry.lock` 文件定义了项目依赖。
- **pnpm**: 仓库使用 pnpm 管理 JavaScript 依赖，`package.json` 和 `pnpm-lock.yaml` 文件定义了前端项目依赖。
- **Virtual Machine (VM)**: README 中提到 "Virtualized Deploy Workflow"，该流程将应用部署到虚拟机，例如 AWS EC2s, GCloud apps, Digital Ocean droplets 等。
- **Bare-metal Deploy Workflow**: README 中提到另一种部署方式，直接将应用部署到物理机，但不推荐。
- **Gunicorn**: `config/supervisor/drt.ini` 文件中使用了 Gunicorn 作为 WSGI 服务器，用于部署 Django 应用。

## 可作为 QA Ground Truth 的高信息密度摘要
该图描述了 Django + React + TypeScript 应用的 CI/CD 流程，从开发者提交代码开始，经过前端后端构建测试、Docker 镜像构建测试发布，然后部署到虚拟机或物理机。其中，构建测试环节会检查代码质量，Docker 镜像发布到 GitHub Packages，部署阶段会拉取 Docker 镜像并执行 Docker Compose 文件，最终更新上线。如果任何环节失败，流水线会被取消，并建议检查系统健康状况。该流程对应仓库中的 GitHub Actions 配置文件和 Docker Compose 文件，体现了自动化部署的完整过程。
