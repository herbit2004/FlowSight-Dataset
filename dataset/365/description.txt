## Diagram Type & Purpose
This is an architecture diagram illustrating the flow of events and data between various services within a Condition Monitoring System (CMS) and a Decision Support System (DSS). It depicts how external events are processed, routed, and used to trigger workflows and actions, ultimately providing insights and support for decision-making. The diagram highlights the interaction between different components, including event sources, rule engines, stateful workflows, and knowledge bases.

## Overall Layout
The diagram is laid out from top to bottom (TB). It starts with external event sources at the top, flows through various processing stages in the middle, and culminates in decision support and actions at the bottom. The primary flow represents the processing of events and the triggering of workflows based on defined rules and conditions.

## High-Density QA Ground Truth Summary
The process begins with external event sources like Email/IMAP, MQTT Devices, Webhooks, File System, and Schedulers sending events to the EventRouterService. The EventRouterService then routes these events to both the RuleEngineService for rule evaluation and the EventBusService (ZeroMQ PUB/SUB) for broader distribution. If a rule is matched by the RuleEngineService, it triggers the RuleActionExecutorService, which can then perform several actions: sending agent/intent messages back to the EventBusService, triggering a prompt action on Claude LLM, and initiating a workflow event in the StatefulWorkflowsService (XState v5). The EventBusService facilitates communication between services like IntentRouterService, DssQueryAdapterService, and BusLoggerService. The IntentRouterService triggers workflows in the StatefulWorkflowsService. The StatefulWorkflowsService interacts with the WorkflowEntryActionService, which can send prompts/scripts to Claude LLM. The DssQueryAdapterService queries the DecisionSupportService, which utilizes KnowledgeGraphService (Quadstore RDF) and VectorStoreService (ChromaDB) for knowledge retrieval and decision support. The system leverages ZeroMQ for asynchronous messaging and XState for managing stateful workflows, enabling a flexible and responsive architecture for condition monitoring and decision support.
