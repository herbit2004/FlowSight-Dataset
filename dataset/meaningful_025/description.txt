## Diagram Type & Purpose
This is a flowchart diagram illustrating the request routing process in a sharded system. It depicts how an incoming request is handled by a GlobalShardManager, routed to an appropriate ShardRouter (A or B), processed by a DataNode, and the result is returned. The diagram serves as a visual representation of the system's architecture and request flow, aiding in understanding and troubleshooting.

## Overall Layout
The diagram is laid out in a top-down (TD) direction. It is hierarchically structured with a GlobalShardManager at the top, followed by ShardRouters and DataNodes. The start node is "Incoming Request" and the end node is "GlobalShardManager: Return Result".

## Subgraphs / Stages
The diagram contains three explicit subgraphs:
- **GlobalShardManager**: Handles the initial request and determines the appropriate shard router.
- **ShardRouter_A**: Receives requests, looks up the shard location, and forwards to DataNode_A.
- **ShardRouter_B**: Receives requests, looks up the shard location, and forwards to DataNode_B.

## Edges, Branches & Convergence
- `A --> B`: Incoming request is passed to check for Tenant ID.
- `B -- Yes --> C`: If Tenant ID is present, extract it.
- `B -- No --> D`: If Tenant ID is not present, use the default Tenant ID.
- `C --> E`: Extracted Tenant ID is used to lookup the shard key range.
- `D --> E`: Default Tenant ID is used to lookup the shard key range.
- `E --> F`: Shard key range lookup result is checked.
- `F -- Yes --> G`: If shard key range is found, route to the appropriate shard router.
- `F -- No --> H`: If shard key range is not found, raise an error.
- `G --> I`: Request is passed to ShardRouter_A.
- `I --> J`: ShardRouter_A looks up the shard location.
- `J --> K`: Shard location lookup result is checked.
- `K -- Yes --> L`: If shard location is found, forward to DataNode_A.
- `K -- No --> M`: If shard location is not found, fallback to ShardRouter_B.
- `M --> N`: Request is passed to ShardRouter_B.
- `N --> O`: ShardRouter_B looks up the shard location.
- `O --> P`: Shard location lookup result is checked.
- `P -- Yes --> Q`: If shard location is found, forward to DataNode_B.
- `P -- No --> R`: If shard location is not found, raise a data inconsistency alert.
- `L --> S`: Request is passed to DataNode_A for processing.
- `Q --> T`: Request is passed to DataNode_B for processing.
- `S --> U`: DataNode_A returns the result.
- `T --> V`: DataNode_B returns the result.
- `U --> W`: ShardRouter_A returns the result.
- `V --> Y`: ShardRouter_B returns the result.
- `W --> X`: ShardRouter_A returns the final result to GlobalShardManager.
- `Y --> X`: ShardRouter_B returns the final result to GlobalShardManager.

## Repository Context & Terminology
- **Sharding**: A database partitioning technique that separates very large databases into smaller, faster, more easily managed parts called data shards.
- **Tenant ID**: An identifier for a specific tenant or customer in a multi-tenant system.
- **Shard Key**: A value used to determine which shard a particular piece of data belongs to.
- **Shard Router**: A component responsible for routing requests to the appropriate shard.
- **DataNode**: A node in the system that stores and processes data for a specific shard.
- **GlobalShardManager**: A central component responsible for managing shards and routing requests.
- **Fallback Router**: A secondary router used when the primary shard location is not found.

## High-Density QA Ground Truth Summary
The process begins with an "Incoming Request" to the "GlobalShardManager". The first decision point is "Tenant ID Present?". If 'Yes', the "Tenant ID" is extracted; if 'No', a "Default Tenant ID" is used. Next, "Lookup Shard Key Range" is performed, and a check "Shard Key Range Found?" determines the subsequent path. If 'Yes', the request is routed to the "Route to Appropriate Shard Router"; if 'No', an "Error: No Shard Key Range" is raised. The request then reaches either "ShardRouter_A" or "ShardRouter_B", where a "ShardRouter Lookup" is performed. A "Shard Location Found?" check determines whether to "Forward to DataNode_A/B" or, in the case of ShardRouter_A, to a "Fallback Router" which then routes to ShardRouter_B. If the shard location is not found in ShardRouter_B, an "Alerting: Data Inconsistency" is triggered. DataNodes process the request and return results to their respective ShardRouters, which then return the final result to the "GlobalShardManager: Return Result" node, completing the flow. Sharding is a key concept here, enabling horizontal scaling by partitioning data across multiple DataNodes, and the ShardRouter ensures requests are directed to the correct partition based on the Tenant ID and Shard Key.
