## 图类型与用途
这是一个流程图，描述了 `django-react-typescript` 项目的裸机部署（Bare-metal Deploy Workflow）流程。它展示了从代码变更到最终部署上线所涉及的步骤，用于概括自动化部署流水线。

## 图的整体布局
图采用从左到右的布局。流程从开发者修改应用开始，经过一系列构建、测试、复制文件、部署和启动服务器的步骤，最终完成更新上线或取消流水线。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可以分为以下几个阶段：
1. **代码变更与提交**：开发者修改代码并提交。
2. **构建与测试**：构建并测试前端和后端。
3. **文件复制**：登录到宿主机并将相关文件复制到宿主机。
4. **宿主机构建与部署**：在宿主机上构建前端和后端，然后部署应用程序。
5. **启动服务器与更新上线**：启动 Gunicorn 服务器并使用 Supervisor 管理，确保系统持续运行。

## 节点逐项说明
- **nv ("Make changes to\nthe application")**：对应用程序进行更改，是流程的起点。
- **n7 ("Build and test frontend\nand backend")**：构建并测试前端（React）和后端（Django）。
- **nf {"Success?"}**：判断构建和测试是否成功，是流程中的一个决策点。
- **n2 ("Logs into host machine\nand copy all relevant files\nfrom repo to it")**：登录到宿主机，并将所有相关文件从代码仓库复制到宿主机上。
- **n5 {"Success?"}**：判断文件复制是否成功。
- **nx ("Builds the frontend\nand the backend")**：在宿主机上构建前端和后端。
- **nj {"Success?"}**：判断在宿主机上的构建是否成功。
- **nd ("Deploy")**：部署应用程序。
- **nc ("Starts gunicorn server under\nsupervisor to ensure the\nsystem is never down")**：启动 Gunicorn 服务器，并使用 Supervisor 进行管理，以确保系统持续运行。参考 `config/supervisor/drt.ini` 文件，该文件配置了 Supervisor 来管理 Gunicorn 进程。
- **na {"Success?"}**：判断 Gunicorn 服务器是否成功启动。
- **nk ("Updates are live")**：更新已生效，表示部署完成。
- **n4 ("Cancel pipeline")**：取消流水线，通常发生在构建或测试失败时。
- **ng ("Better manually log in\ninto host and fix it")**：建议手动登录到宿主机并进行修复，通常发生在部署或启动服务器失败时。

## 连线、分支与汇聚关系
- `nv -- Commit --> n7`：开发者提交代码更改后，触发构建和测试流程。
- `n7 --> nf{"Success?"}`：构建和测试完成后，进入成功判断环节。
- `nf -- Yes --> n2`：如果构建和测试成功，则登录到宿主机并复制文件。
- `nf -- No --> n4`：如果构建和测试失败，则取消流水线。
- `n2 --> n5{"Success?"}`：文件复制完成后，进入成功判断环节。
- `n5 -- No --> n4`：如果文件复制失败，则取消流水线。
- `n5 -- Yes --> nx`：如果文件复制成功，则在宿主机上构建前端和后端。
- `nx --> nj{"Success?"}`：宿主机构建完成后，进入成功判断环节。
- `nj -- No --> n4`：如果宿主机构建失败，则取消流水线。
- `nj -- Yes --> nd`：如果宿主机构建成功，则部署应用程序。
- `nd --> nc`：部署完成后，启动 Gunicorn 服务器并使用 Supervisor 管理。
- `nc --> na{"Success?"}`：Gunicorn 服务器启动后，进入成功判断环节。
- `na -- No --> ng`：如果 Gunicorn 服务器启动失败，则建议手动登录到宿主机进行修复。
- `na -- Yes --> nk`：如果 Gunicorn 服务器启动成功，则更新生效。

## 仓库语境与术语解释
- **Bare-metal Deploy Workflow**：指直接在物理服务器上部署应用程序，不使用虚拟化技术。该流程在 `README.md` 中被提及，并对应 `deploy-bare-metal.yml` GitHub Actions workflow。
- **Gunicorn**：一个 Python WSGI HTTP 服务器，用于部署 Django 应用程序。`config/supervisor/drt.ini` 文件配置了 Gunicorn 的启动命令。
- **Supervisor**：一个进程管理工具，用于监控和管理 Gunicorn 进程，确保系统持续运行。
- **GitHub Actions**：GitHub 提供的 CI/CD 服务，用于自动化构建、测试和部署流程。该项目使用 GitHub Actions 来实现裸机部署流水线，相关配置文件位于 `.github/workflows/` 目录下。
- **Dockerfile**：用于构建 Docker 镜像的配置文件。该项目使用 Dockerfile 来构建包含前端和后端应用程序的镜像。
- **docker-compose.yml**：用于定义和管理多个 Docker 容器的配置文件。该项目使用 docker-compose.yml 来管理 Web 应用、Postgres 数据库和 Memcached 缓存。
- **pnpm**：一个 Node.js 包管理器，用于管理前端项目的依赖。
- **Poetry**：一个 Python 依赖管理工具，用于管理后端项目的依赖。

## 可作为 QA Ground Truth 的高信息密度摘要
该图描述了 `django-react-typescript` 项目的裸机部署流程。流程从开发者修改代码并提交开始，经过构建和测试，若成功则登录宿主机并复制文件，然后在宿主机上构建前后端并部署。部署后，启动 Gunicorn 服务器并使用 Supervisor 管理，若启动成功则更新生效，否则建议手动登录宿主机修复。其中，Gunicorn 和 Supervisor 是确保应用稳定运行的关键组件，而 GitHub Actions 自动化了整个部署流程。`README.md` 提到了该部署流程，并提供了相应的 GitHub Actions workflow 文件。
