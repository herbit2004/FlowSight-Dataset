## Edges, Branches & Convergence
- `A --> B`: User application sends a request to the API Gateway.
- `B --> C`: API Gateway forwards the request to the Rate Limit Check.
- `C -- Within Limit --> D`: Request is within the rate limit, route to Request Router.
- `C -- Exceeds Limit --> E`: Request exceeds the rate limit, return 429 error.
- `D --> F`: Request Router forwards the request to the Model Version check.
- `F -- Versioned --> G`: Use Model A if a specific version is requested.
- `F -- Latest --> H`: Use Model B (latest version) if no version is specified.
- `G --> GA`: Model A Inference forwards the request to Pre-processing A.
- `GA --> GB`: Pre-processing A forwards the request to Model A Core.
- `GB --> GC`: Model A Core forwards the request to Post-processing A.
- `H --> HA`: Model B Inference forwards the request to Pre-processing B.
- `HA --> HB`: Pre-processing B forwards the request to Model B Core.
- `HB --> HC`: Model B Core forwards the request to Post-processing B.
- `GC --> I`: Post-processing A forwards the output to the Ensemble check.
- `HC --> I`: Post-processing B forwards the output to the Ensemble check.
- `I -- Yes --> J`: Ensemble processing is required, route to Ensemble Stage.
- `I -- No --> K`: Ensemble processing is not required, route to Response Builder.
- `J --> K`: Ensemble Stage forwards the output to the Response Builder.
- `K --> L`: Response Builder forwards the response to the API Gateway.
- `L --> M`: API Gateway sends the response back to the User Application.

## Repository Context & Terminology
- **API Gateway**: A service that acts as a single entry point for all API requests, handling routing, authentication, and rate limiting.
- **Rate Limiting**: A mechanism to control the number of requests a user can make within a given time period, preventing abuse and ensuring service availability.
- **Model Inference**: The process of using a trained machine learning model to generate predictions on new data.
- **Pre-processing**: Data transformation steps applied to the input data before feeding it to the model.
- **Post-processing**: Data transformation steps applied to the model's output to make it more usable or presentable.
- **Ensemble**: A technique that combines the predictions of multiple models to improve overall accuracy and robustness.
- **Response Builder**: A component responsible for formatting the model's output into a standardized API response.
- **429 Too Many Requests**: An HTTP status code indicating that the user has sent too many requests in a given amount of time.

## High-Density QA Ground Truth Summary
The flowchart begins with a "User Application" sending a request to the "API Gateway". The API Gateway then performs a "Rate Limit Check". If the request is "Within Limit", it proceeds to the "Request Router"; otherwise, a "429" error is returned. The "Request Router" then determines the "Model Version". Depending on the version ("Versioned" or "Latest"), the request is routed to either "Model A Inference" or "Model B Inference", respectively. Both models have their own pre-processing, core inference, and post-processing stages (e.g., "Pre-processing A", "Model A Core", "Post-processing A"). After model-specific processing, an "Ensemble?" check determines if the outputs need to be combined. If "Yes", the request goes to the "Ensemble Stage"; otherwise, it proceeds directly to the "Response Builder". The "Ensemble Stage" also feeds into the "Response Builder". Finally, the "Response Builder" constructs the response, which is sent back to the "API Gateway" and then to the "User Application". The API Gateway component is a critical element, handling initial request routing, rate limiting, and final response delivery, often implemented using technologies like Kong or AWS API Gateway.
