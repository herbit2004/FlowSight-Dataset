## Diagram Type & Purpose
This is an architecture diagram illustrating a multi-region application deployment with failover capabilities. It depicts the flow of user requests, load balancing, application server interactions, and database replication across two regions (Region A and Region B). The diagram highlights the failover mechanism from Region A to Region B in case of failures.

## Overall Layout
The diagram is laid out from top to bottom (TB). It is divided into subgraphs representing different regions and monitoring components. The primary flow starts with a user request in Region A and can end with data being written to the primary database or the request being handled by Region B in a failover scenario, with data replicated to the read replica database.

## Subgraphs / Stages
The diagram contains three subgraphs:
- **Region A**: Represents the primary region handling user requests.
- **Region B**: Represents the standby region used during failover.
- **Monitoring**: Represents the monitoring system responsible for health checks and failure detection.

## Repository Context & Terminology
- **Load Balancer**: A network device or software that distributes network traffic across multiple servers to ensure no single server is overwhelmed.
- **Application Server**: A server that hosts and runs applications.
- **Database Primary**: The main database server that handles read and write operations.
- **Database Read Replica**: A read-only copy of the primary database, used to offload read operations and improve performance.
- **Failover**: The process of automatically switching to a redundant or standby system upon the failure of a primary system.
- **Asynchronous Replication**: A method of database replication where changes to the primary database are applied to the replica database with a delay.
- **Health Checks**: Automated tests to verify the availability and performance of a system or component.
- **Metrics**: Quantifiable measurements used to track and assess the performance and health of a system.

## High-Density QA Ground Truth Summary
The process begins with a `User Request` directed to `Load Balancer A` in `Region A`. The `Load Balancer A` then routes the request to either `Application Server A1` or `Application Server A2`, assuming healthy instances are available. If `Load Balancer A` detects no healthy instances, a `Failover` is triggered. The `Monitoring` system continuously performs `Health Checks & Metrics` on both regions, and if it `Detects region failure`, it also initiates the `Failover`. The `Failover` process then signals `Load Balancer B` in `Region B`. Alternatively, a `Standby User Request - Rarely Used` can directly target `Load Balancer B`. `Load Balancer B` distributes requests to `Application Server B1` or `Application Server B2`. `Application Server A1` and `Application Server A2` perform `DB Read/Write` operations against the `Database Primary`, while `Application Server B1` and `Application Server B2` perform `DB Read Only` operations against the `Database Read Replica`. The `Database Primary` asynchronously replicates its data to the `Database Read Replica` to maintain data consistency. The system architecture ensures high availability by utilizing a standby region and database replication, allowing the application to continue serving requests even if the primary region experiences failures.
