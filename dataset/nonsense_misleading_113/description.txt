## Diagram Type & Purpose
This is a flowchart diagram depicting the order processing workflow. It illustrates the sequence of steps from when a user places an order to when the order is delivered or cancelled. The diagram serves as a visual representation of the order fulfillment process, including payment verification, inventory checks, shipping, and delivery confirmation.

## Overall Layout
The diagram's primary direction is top-down (TD). It starts with the "User Places Order" node at the top and flows downwards through a series of processes and decision points. The end nodes are "Order Cancelled," "Notify User of Delay," and "Update Order Status."

## Subgraphs / Stages
No explicit subgraphs; logically divided into 5 stages: Order Placement & Payment, Inventory & Packaging, Shipping & Confirmation, Delivery & Feedback, and Error Handling.

## Edges, Branches & Convergence
- `A --> B`: The user's order is sent for payment verification.
- `B -- No --> C`: If payment is not received, the order is cancelled.
- `B -- Yes --> D`: If payment is received, an inventory check is performed.
- `D --> E`: The inventory check result is used to determine if there is sufficient stock.
- `E -- No --> F`: If there is insufficient stock, the user is notified of a delay.
- `E -- Yes --> G`: If there is sufficient stock, the order is packaged.
- `G --> H`: After packaging, a shipping label is created.
- `H --> J`: The shipping label triggers sending shipping confirmation.
- `J -- No --> G`: If shipping confirmation is not sent, the process loops back to packaging the order.
- `J -- Yes --> K`: If shipping confirmation is sent, the order is marked as shipped.
- `K --> L`: The order is shipped and delivered.
- `L --> M`: Delivery confirmation is checked.
- `M -- No --> N`: If delivery is not confirmed, an investigation is initiated.
- `N --> L`: After investigation, the process loops back to the package delivered node.
- `M -- Yes --> P`: If delivery is confirmed, the order status is updated.
- `P --> Q`: After updating the order status, a feedback request is sent.
- `Q --> F`: Sending a feedback request triggers notifying the user of a delay.
- `C --> Q`: Order cancellation triggers sending a feedback request.

## Repository Context & Terminology
- **User Places Order**: Standard meaning is a customer submitting an order for goods or services. In this diagram, it's the starting point of the order processing workflow.
- **Payment Received?**: Standard meaning is verifying if the payment has been successfully processed. In this diagram, it's a decision point that determines whether the order proceeds or is cancelled.
- **Inventory Check**: Standard meaning is verifying the availability of items in stock. In this diagram, it's a process to ensure sufficient stock before packaging.
- **Sufficient Stock?**: Standard meaning is determining if there are enough items to fulfill the order. In this diagram, it's a decision point that leads to either notifying the user of a delay or proceeding with packaging.
- **Shipping Confirmation Sent?**: Standard meaning is confirming that the shipping details have been sent to the customer. In this diagram, it occurs *before* the shipping label is created, and if the confirmation isn't sent, the process loops back to packaging the order.
- **Delivery Confirmed?**: Standard meaning is verifying that the customer has received the package. In this diagram, if delivery is not confirmed, an investigation is initiated, and the process loops back to the "Package Delivered" node.
- **Send Feedback Request**: Standard meaning is requesting feedback from the customer about their experience. In this diagram, it is triggered after updating the order status and also after order cancellation, and it causes a notification of delay to be sent to the user.

## High-Density QA Ground Truth Summary
The order processing workflow begins with the "User Places Order" node (A), which leads to the "Payment Received?" decision point (B). If payment is not received, the order is cancelled (C), and a feedback request is sent (Q), which then incorrectly triggers a notification of delay (F). If payment is received, an inventory check (D) is performed. If there is insufficient stock, the user is notified of a delay (F). If there is sufficient stock, the order is packaged (G), and a shipping label is created (H). Illogically, shipping confirmation is sent (J) *before* the label is created. If delivery is not confirmed, an investigation is initiated (N), and the process loops back to the "Package Delivered" node (L). If delivery is confirmed, the order status is updated (P), and a feedback request is sent (Q), which incorrectly triggers a notification of delay (F). The end nodes are "Order Cancelled" (C), "Notify User of Delay" (F), and "Update Order Status" (P). The reversed sequence of shipping confirmation before label creation and the illogical loop back to packaging if confirmation fails highlight the diagram's counterfactual nature.
