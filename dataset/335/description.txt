## 图类型与用途
这是一个流程图，描述了软件开发过程中的 QA（质量保证）反馈循环，对应 README 中的 “P7 QA 피드백 루프 상세”。它展示了发现问题后，如何将问题分配给不同的专家进行修复，并最终完成 QA 流程。

## 图的整体布局
图整体采用从上到下的布局。流程从顶部的 QA 阶段开始，经过问题解析、优先级判断、专家分配、修复验证等环节，最终结束于循环结束或问题升级。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可分为四个阶段：问题发现与解析、问题分发、问题修复与验证、循环控制与升级。

## 节点逐项说明
- **QA ("기능 QA + 보안 QA")**：功能和安全性的质量保证阶段，是流程的起点，负责发现问题。对应 README 中 P7 阶段的 qa-tester 角色。
- **PARSE ("FINDINGS 파싱")**：对 QA 阶段发现的问题（FINDINGS）进行解析，提取关键信息。
- **CHECK {"CRITICAL/HIGH?"}**：检查解析出的问题是否属于“严重”或“高优先级”级别。这是一个判断节点。
- **DONE ("루프 종료 ✅")**：如果问题不属于严重或高优先级，则流程结束，表示问题已处理完毕。
- **MAP ("Finding→Specialist 매핑")**：如果问题属于严重或高优先级，则将问题映射到相应的专家。根据问题类型，分配给不同的专家。对应 README 中的 “Finding → Specialist 매핑 규칙”。
- **UI ("UI → frontend")**：将 UI 相关的问题分配给前端专家。对应 README 中 frontend-specialist 角色。
- **API ("API → backend")**：将 API 相关的问题分配给后端专家。对应 README 中 backend-specialist 角色。
- **DB ("DB → supabase")**：将数据库相关的问题分配给 supabase 专家。对应 README 中 supabase-specialist 角色。
- **PERF ("PERF → optimizer")**：将性能相关的问题分配给优化专家。对应 README 中 performance-optimizer 角色。
- **SEC ("SEC → security")**：将安全相关的问题分配给安全专家。对应 README 中 security-specialist 角色。
- **BUG ("TYPE → bug-fixer")**：将一般 Bug 分配给 Bug 修复人员。对应 README 中 bug-fixer 角色。
- **BUILD ("빌드/타입 검증")**：在专家修复问题后，进行构建和类型验证，确保修复后的代码没有引入新的问题。
- **CYCLE {"Cycle < 3?"}**：检查 QA 循环次数是否小于 3 次。这是一个判断节点，用于限制循环次数。
- **ESC ("사용자 에스컬레이션 ⚠️")**：如果 QA 循环次数超过 3 次，则将问题升级给用户，可能需要更高级别的干预。对应 README 中的 “에스컬레이션”。

## 连线、分支与汇聚关系
- `QA -> PARSE`：QA 阶段发现问题，并将问题传递给 PARSE 节点进行解析。
- `PARSE -> CHECK`：PARSE 节点将解析后的问题传递给 CHECK 节点，判断问题的严重程度。
- `CHECK -- NO --> DONE`：如果问题不严重，则流程结束（DONE）。
- `CHECK -- YES --> MAP`：如果问题严重，则 MAP 节点将问题分配给相应的专家。
- `MAP -> UI`：将 UI 相关的问题分配给前端专家。
- `MAP -> API`：将 API 相关的问题分配给后端专家。
- `MAP -> DB`：将数据库相关的问题分配给 supabase 专家。
- `MAP -> PERF`：将性能相关的问题分配给优化专家。
- `MAP -> SEC`：将安全相关的问题分配给安全专家。
- `MAP -> BUG`：将一般 Bug 分配给 Bug 修复人员。
- `UI -> BUILD`：UI 专家修复问题后，BUILD 节点进行构建和类型验证。
- `API -> BUILD`：API 专家修复问题后，BUILD 节点进行构建和类型验证。
- `DB -> BUILD`：DB 专家修复问题后，BUILD 节点进行构建和类型验证。
- `PERF -> BUILD`：PERF 专家修复问题后，BUILD 节点进行构建和类型验证。
- `SEC -> BUILD`：SEC 专家修复问题后，BUILD 节点进行构建和类型验证。
- `BUG -> BUILD`：BUG 专家修复问题后，BUILD 节点进行构建和类型验证。
- 多个专家节点（UI, API, DB, PERF, SEC, BUG）汇聚到 BUILD 节点，形成汇聚关系。
- `BUILD -> CYCLE`：BUILD 节点将验证结果传递给 CYCLE 节点，判断 QA 循环次数是否超过限制。
- `CYCLE -- YES --> QA`：如果循环次数未超过限制，则流程返回 QA 阶段，进行新一轮的 QA 测试。
- `CYCLE -- NO --> ESC`：如果循环次数超过限制，则流程进入 ESC 节点，将问题升级。

## 仓库语境与术语解释
- **QA (Quality Assurance)**：质量保证，是软件开发过程中的一个阶段，旨在发现和修复软件中的缺陷。
- **FINDINGS**：QA 阶段发现的问题，对应 README 中 “P7 QA 피드백 루프 상세”。
- **Specialist**：专家，指负责修复特定类型问题的开发人员，例如前端专家、后端专家、数据库专家等。对应 README 中 “Agent” 的概念。
- **빌드/타입 검증 (Build/Type Verification)**：构建和类型验证，指在专家修复问题后，进行代码构建和类型检查，确保修复后的代码没有引入新的问题。
- **에스컬레이션 (Escalation)**：升级，指当 QA 循环次数超过限制时，将问题升级给用户，可能需要更高级别的干预。对应 README 中 “Severity별 처리 규칙”。
- **Cycle < 3?**：图中可见，但 README 上下文表明，如果循环次数超过 3 次，则会进行用户升级。
- **Hook**：README 中提到，P7 阶段的核心 Hook 包括 `auto-validate` 和 `sql-check`，用于自动化验证和安全检查。

## 可作为 QA Ground Truth 的高信息密度摘要
该图描述了 Manager-Orchestrator 系统中的 QA 反馈循环流程，从 QA 阶段发现问题开始，经过问题解析和优先级判断，将问题分配给不同的专家进行修复，修复后的代码经过构建和类型验证，如果 QA 循环次数未超过 3 次，则返回 QA 阶段进行新一轮测试，否则将问题升级。其中，问题的严重程度判断和专家分配是关键分支，构建和类型验证是核心中间环节，最终结果是问题修复或用户升级。该流程对应 README 中的 P7 阶段，并受到 Hook 机制的约束。
