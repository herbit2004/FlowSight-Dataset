## Edges, Branches & Convergence
- `A --> B`: Customer places an order, initiating the payment check.
- `B -- No --> C`: If payment is not received, the order is cancelled due to insufficient funds.
- `B -- Yes --> D`: If payment is received, proceed to inventory check.
- `D -- Available --> E`: If the inventory is available, validate the shipping address.
- `D -- Unavailable --> F`: If the inventory is unavailable, request a supplier restock.
- `F --> H`: Requesting a supplier restock leads to production completion and inventory update.
- `H --> D`: Production completion and inventory update then loops back to the inventory check.
- `E -- Invalid --> G`: If the shipping address is invalid, contact the customer for an address update.

- `K --> M`: After shipping the order, check if the order has been delivered.
- `M -- Yes --> N`: If the order has been delivered, send an order completion email.

## Repository Context & Terminology
- **Order**: A request from a customer to purchase goods or services. In this diagram, it represents the entire process from placement to completion, but the diagram contains several logical errors.
- **Payment Received?**: A check to ensure that the customer has paid for the order. In reality, this is a crucial step, but in this diagram, the flow loops back to this check after analytics are updated.
- **Inventory Check**: A process to verify the availability of items in stock. In this diagram, the production completion and inventory update *causes* the inventory check, which is incorrect.
- **Shipping Address Validation**: Verifying that the customer's provided address is correct and deliverable. In this diagram, an invalid address loops back to validation after customer contact, not to the subsequent order processing steps.

## High-Density QA Ground Truth Summary
The flowchart begins with a "Customer Places Order," which leads to a "Payment Received?" check. If payment is not received, the "Order Cancelled - Insufficient Funds" node is reached. If payment is received, an "Inventory Check" is performed. If inventory is unavailable, a "Request Supplier Restock" is triggered, leading to "Production Complete & Inventory Updated," which then loops back to the "Inventory Check." If inventory is available, the "Shipping Address Validated" node is reached. An invalid address results in "Contact Customer for Address Update," looping back to "Shipping Address Validated." A valid address leads to "Order Packed," followed by a "Shipping Label Printed?" check. If the label is not printed, "Contact Customer Service" is triggered, looping back to the label check. Illogically, if the label *is* printed, the flow goes to "Order Shipped - Tracking Sent," followed by "Order Delivered?". If the order is not delivered, "Investigate Shipping Delay" loops back to the delivery check. If delivered, "Order Completion Email Sent" leads to "Customer Satisfied?". If the customer is *not* satisfied, "Open Support Ticket" leads to "Issue Refund," which loops back to the satisfaction check. If the customer *is* satisfied, "System Log: Order Complete" leads to "Analytics Data Updated," which then loops back to the initial "Payment Received?" check, creating a closed loop. The diagram contains reversed logic, incorrect causal directions, and an illogical loop, deviating from standard order processing workflows.
