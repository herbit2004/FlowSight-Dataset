## 图类型与用途
这是一个流程图，展示了“架构即代码”方法中，架构决策、架构结构、规范、代码实现和验证之间的迭代关系。它描述了一个开发流程，强调架构文档与代码实现紧密结合，确保架构设计与代码实现保持一致。

## 图的整体布局
图整体采用从左到右的循环布局。流程从架构决策（ADR）开始，经过架构结构（C4 View）、开放规范（OpenSpec）、代码实现（Code），再到测试（Tests），最终测试结果反馈回架构决策（ADR），形成闭环。

## 分组/子图/阶段说明
图中没有显式子图/分组，但逻辑上可以分为架构决策阶段、架构设计阶段、代码实现阶段和验证阶段。

## 节点逐项说明
- **ADR (Decision)**：架构决策记录，记录了架构选择的原因和背景。根据 README，ADRs document *why* decisions were made。
- **C4 View (Structure)**：C4模型视图，描述了系统的静态结构，包括容器、组件和代码元素之间的关系。根据 README，C4 diagrams show *what* the system looks like。
- **OpenSpec (Specification)**：开放规范，详细定义了系统组件的行为和接口。根据 README，OpenSpec is a specification methodology designed for spec-driven development with AI。
- **Code (Implementation)**：代码实现，即根据规范编写的实际代码。
- **Tests (Verification)**：测试，用于验证代码是否符合规范，并确保系统按照预期运行。

## 连线、分支与汇聚关系
- `ADR -> C4`：架构决策指导C4视图的创建，箭头上的文字 "Documents why" 表明ADR解释了C4视图中架构选择的原因。
- `C4 -> OpenSpec`：C4视图定义了开放规范，箭头上的文字 "Shows how" 表明C4视图展示了如何实现架构决策。
- `OpenSpec -> Code`：开放规范作为代码实现的指南，箭头上的文字 "Defines what" 表明OpenSpec定义了代码需要实现的内容。
- `Code -> Tests`：代码实现完成后，需要进行测试以验证其正确性，箭头上的文字 "Implements" 表明代码实现了规范。
- `Tests -> OpenSpec`：测试结果用于验证代码是否符合开放规范，箭头上的文字 "Validates against" 表明测试验证代码是否符合规范。
- `Tests -> ADR`：测试结果反馈到架构决策记录中，如果测试发现架构设计存在问题，则需要重新评估和修改架构决策，箭头上的文字 "Feeds back to" 表明测试结果可以影响架构决策。

## 仓库语境与术语解释
- **ADR (Architecture Decision Record)**：用于记录架构决策，参见 `docs/architecture/adr/README.md`。
- **C4 Model**：一种分层架构图，包括 System Context, Container, Component 等层级，参见 `docs/architecture/c4-views/README.md`。
- **OpenSpec**：一种规范方法，用于规范驱动的AI开发，参见 `openspec/README.md`。
- **Architecture as Code**：一种将架构文档作为代码进行维护的方法，该仓库是一个完整的示例。
- **Structurizr DSL**：用于编写 C4 视图的领域特定语言，参见 `docs/architecture/c4-views/structurizr-dsl/` 目录。
- **MADR (Markdown ADR)**：一种使用 Markdown 格式编写 ADR 的规范，参见 `docs/architecture/adr/README.md`。

## 可作为 QA Ground Truth 的高信息密度摘要
该图展示了一个以架构决策为中心的迭代开发流程，从 ADR 开始，经过 C4 视图、OpenSpec、代码实现，最终通过测试验证并反馈回 ADR，形成闭环。其中，ADR 记录决策原因，C4 视图展示系统结构，OpenSpec 定义组件行为，测试验证代码是否符合规范。该流程强调架构文档与代码实现紧密结合，确保架构设计与代码实现保持一致。该图体现了“架构即代码”的核心思想。
