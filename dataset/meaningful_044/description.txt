## Diagram Type & Purpose
This is a flowchart diagram illustrating a multi-tenant data access pattern. It depicts the flow of a user request through authorization, data access layers, a shared infrastructure, and ultimately to a response. The diagram highlights how data is filtered and accessed based on tenant ID in a multi-tenant environment.

## Overall Layout
The diagram is laid out from top to bottom (TB). It is divided into two main sections representing Tenant A and Tenant B, with a shared infrastructure section in the middle. The start nodes are the user requests for each tenant, and the end nodes are the application responses for each tenant.

## Subgraphs / Stages
The diagram contains two explicit subgraphs: Tenant A and Tenant B, representing the request flow for each tenant. There is also a "Shared Infrastructure" subgraph, representing the common components used by both tenants.

## Repository Context & Terminology
- **Multi-Tenancy**: A software architecture where a single instance of the software serves multiple customers (tenants).
- **Data Access Layer**: An abstraction layer that provides simplified access to data stored in a database or other data storage system.
- **Authorization**: The process of verifying that a user or application has the necessary permissions to access a resource.
- **Data Filtering**: The process of selecting a subset of data based on specific criteria, such as tenant ID.
- **Data Access Router**: A component that routes data access requests to the appropriate data source or service based on tenant ID or other criteria.
- **Tenant ID**: A unique identifier for each tenant in a multi-tenant system.
- **Shared Infrastructure**: The common hardware and software resources that are shared by all tenants in a multi-tenant system.

## High-Density QA Ground Truth Summary
The process begins with either a `User: Tenant A Request` or a `User: Tenant B Request`, which immediately triggers an `Authorization Check` specific to that tenant. If the authorization check passes (`Allowed`), the request proceeds to the tenant-specific `Data Access Layer`. If the authorization fails (`Denied`), a `Return Error: Unauthorized` is generated, which is then passed to the respective `Application: Tenant A/B Response`. When authorized, the `Data Access Layer` forwards the request to the `Data Access Router` within the `Shared Infrastructure`. The `Data Access Router` uses the `Tenant A/B ID` to route the request to the appropriate `Filter Data by Tenant A/B` component. The filtered request is then sent to the `Multi-Tenant Database`. The database returns the requested data, which is then passed to the `Return Filtered Data: Tenant A/B` component. Finally, the filtered data is returned as the `Application: Tenant A/B Response`. The `Multi-Tenant Database` is a key component, allowing multiple tenants to share the same database instance while maintaining data isolation through tenant-specific filtering. The `Data Access Router` ensures that requests are routed to the correct filter based on the tenant ID, maintaining data security and isolation.
