## 图类型与用途
这是一个流程图，描述了 `Pingap` 反向代理服务器处理 HTTP 请求的流程。它展示了请求如何根据 Host 和 Path 路由到不同的上游服务器，并应用不同的插件，体现了 `Pingap` 作为反向代理的核心路由功能。

## 图的整体布局
图整体采用从上到下的布局。顶部是请求的起始点，中间是路由选择、插件执行和上游服务器处理阶段，底部是响应和日志记录。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可以分成三个阶段：请求接收与路由、插件处理与上游转发、响应处理与日志记录。

## 节点逐项说明
- **New Request**：表示新的 HTTP 请求的起始点。
- **HTTP Server**：代表 `Pingap` 反向代理服务器，接收所有新的 HTTP 请求。
- **Location A**：代表服务器上配置的一个 Location，对应 `host:HostA, Path:/api/*` 的请求，用于路由匹配。
- **Location B**：代表服务器上配置的另一个 Location，对应 `Path:/rest/*` 的请求，用于路由匹配。
- **Proxy Plugin List A**：代表在 Location A 上配置的代理插件列表。这些插件在请求被转发到上游服务器之前执行，用于实现各种功能，例如认证、安全检查、流量控制等。
- **Proxy Plugin List B**：代表在 Location B 上配置的代理插件列表。这些插件在请求被转发到上游服务器之前执行，用于实现各种功能。
- **Upstream A1**：代表 Location A 对应的上游服务器，代理地址为 `10.0.0.1:8001`。
- **Upstream A2**：代表 Location A 对应的另一个上游服务器，代理地址为 `10.0.0.2:8001`。
- **Upstream B1**：代表 Location B 对应的上游服务器，代理地址为 `10.0.0.1:8002`。
- **Upstream B2**：代表 Location B 对应的另一个上游服务器，代理地址为 `10.0.0.2:8002`。
- **Response Plugin List A**：代表在 Location A 上配置的响应插件列表。这些插件在上游服务器返回响应后执行，用于修改响应内容、添加头部等。
- **Response Plugin List B**：代表在 Location B 上配置的响应插件列表。这些插件在上游服务器返回响应后执行，用于修改响应内容、添加头部等。
- **HTTP Response**：代表最终的 HTTP 响应。
- **Logging**：表示请求处理结束，进行日志记录。

## 连线、分支与汇聚关系
- `New Request -> HTTP Server`：新的 HTTP 请求到达 HTTP 服务器。
- `HTTP Server -- "host:HostA, Path:/api/*" --> Location A`：服务器根据 Host 和 Path 将请求路由到 Location A。
- `HTTP Server -- "Path:/rest/*" --> Location B`：服务器根据 Path 将请求路由到 Location B。
- `Location A -- "Exec Proxy Plugins" --> Proxy Plugin List A`：Location A 执行其对应的代理插件列表。
- `Location B -- "Exec Proxy Plugins" --> Proxy Plugin List B`：Location B 执行其对应的代理插件列表。
- `Proxy Plugin List A -- "proxy pass: 10.0.0.1:8001" --> Upstream A1`：代理插件列表将请求代理到 Upstream A1。
- `Proxy Plugin List A -- "proxy pass: 10.0.0.2:8001" --> Upstream A2`：代理插件列表将请求代理到 Upstream A2。
- `Proxy Plugin List A -- "done" --> HTTP Response`：代理插件列表执行完成后，直接返回响应。
- `Proxy Plugin List B -- "proxy pass: 10.0.0.1:8002" --> Upstream B1`：代理插件列表将请求代理到 Upstream B1。
- `Proxy Plugin List B -- "proxy pass: 10.0.0.2:8002" --> Upstream B2`：代理插件列表将请求代理到 Upstream B2。
- `Proxy Plugin List B -- "done" --> HTTP Response`：代理插件列表执行完成后，直接返回响应。
- `Upstream A1 -- "Exec Response Plugins" --> Response Plugin List A`：Upstream A1 返回响应后，执行对应的响应插件列表。
- `Upstream A2 -- "Exec Response Plugins" --> Response Plugin List A`：Upstream A2 返回响应后，执行对应的响应插件列表。
- `Upstream B1 -- "Exec Response Plugins" --> Response Plugin List B`：Upstream B1 返回响应后，执行对应的响应插件列表。
- `Upstream B2 -- "Exec Response Plugins" --> Response Plugin List B`：Upstream B2 返回响应后，执行对应的响应插件列表。
- `Response Plugin List A --> HTTP Response`：响应插件列表处理完成后，生成 HTTP 响应。
- `Response Plugin List B --> HTTP Response`：响应插件列表处理完成后，生成 HTTP 响应。
- `HTTP Response --> Logging`：最终，经过处理的响应返回给客户端，并进行日志记录。

## 仓库语境与术语解释
- **Pingap**：一个高性能反向代理，由 Cloudflare Pingora 提供支持。它通过 TOML 文件和 Web 管理界面简化了操作管理，支持动态、零停机的配置热重载，如 README 所述。
- **Location**：在 `Pingap` 中，Location 用于根据请求的 Host 和 Path 进行路由选择。配置文件 `conf/locations.toml` 中定义了 Location 的各种属性，例如 upstream、path、host、plugins 等。
- **Upstream**：代表上游服务器，`Pingap` 将请求代理到这些服务器。`conf/upstreams.toml` 文件中定义了 Upstream 的地址列表、负载均衡算法、健康检查等配置。
- **Plugin**：`Pingap` 的核心特性之一，提供了丰富的功能，例如认证、安全、流量控制等。插件可以在 Location 中配置，并在请求处理的不同阶段执行。
- **Proxy Pass**：图中 `Proxy Plugin List A/B` 到 `Upstream A1/A2/B1/B2` 的连线上标明了 `proxy pass`，表示将请求代理到指定的上游服务器。
- **TOML**：`Pingap` 使用 TOML 格式的配置文件，易于阅读和编写。
- **Cloudflare Pingora**：`Pingap` 基于 Cloudflare Pingora 构建，Pingora 是一个高性能的异步网络库。

## 可作为 QA Ground Truth 的高信息密度摘要
该图展示了 `Pingap` 反向代理服务器处理 HTTP 请求的流程：从接收 `New Request` 开始，`HTTP Server` 根据请求的 Host 和 Path 将请求路由到不同的 `Location`（A 或 B），每个 Location 会执行其对应的 `Proxy Plugin List`，然后根据配置将请求代理到不同的 `Upstream` 服务器。上游服务器返回响应后，会执行对应的 `Response Plugin List`，最终生成 `HTTP Response` 并进行 `Logging`。`Pingap` 通过 Location 和 Plugin 机制实现了灵活的路由和请求处理，配置文件如 `conf/locations.toml` 和 `conf/upstreams.toml` 定义了路由规则和上游服务器配置。
