## Edges, Branches & Convergence
- `A --> B`: Data flows from the sensor data source to raw data ingestion.
- `B --> C`: Raw data is passed to the data quality check.
- `C -- Valid Data --> D`: Valid data is passed to real-time transformation.
- `C -- Invalid Data --> E`: Invalid data triggers the alerting system.
- `E --> N`: The alerting system notifies the operations team.
- `D --> F`: Transformed data is passed to feature extraction.
- `F --> G`: Extracted features are passed to aggregation logic.
- `G -- Per-Widget Aggregation --> H`: Data is aggregated for specific widgets and stored in the widget data store.
- `G -- System-Wide Aggregation --> I`: Data is aggregated for system-wide performance metrics and stored in the system performance store.
- `H --> J`: Widget data is served through the dashboard API endpoint.
- `I --> K`: System performance data is served through the monitoring API endpoint.
- `J --> L`: The dashboard API endpoint provides data to the real-time dashboard.
- `K --> M`: The monitoring API endpoint provides data to the admin monitoring UI.

## Repository Context & Terminology
- **Sensor Data Source**: The origin of the data being processed, typically physical sensors or external data feeds.
- **Raw Data Ingestion**: The process of receiving and initially storing data in its original format.
- **Data Quality Check**: A process to ensure data meets predefined quality standards, including completeness, accuracy, and consistency.
- **Real-Time Transformation**: Converting data into a format suitable for analysis and feature extraction with minimal latency.
- **Feature Extraction**: Identifying and isolating relevant attributes or characteristics from the transformed data.
- **Aggregation Logic**: Combining data points to produce summary statistics or metrics.
- **Widget Data Store**: A database or storage system optimized for serving data to individual dashboard widgets.
- **System Performance Store**: A database or storage system optimized for storing and retrieving system-wide performance metrics.
- **API Endpoint**: A specific URL that provides access to data or functionality.
- **Real-Time Dashboard**: A user interface that displays data with minimal delay, providing up-to-date insights.
- **Admin Monitoring UI**: A user interface that allows administrators to monitor the health and performance of the system.
- **Alerting System**: A system that automatically generates notifications when predefined conditions are met, indicating potential issues.
- **Operations Team**: The team responsible for maintaining the system and responding to alerts.

## High-Density QA Ground Truth Summary
The real-time dashboard data pipeline begins with the "Sensor Data Source," which feeds into "Raw Data Ingestion." The ingested data then undergoes a "Data Quality Check." If the data is valid, it proceeds to "Real-Time Transformation" and "Feature Extraction." If the data is invalid, the "Alerting System" is triggered, notifying the "Operations Team." After feature extraction, the data reaches "Aggregation Logic," where it branches into "Per-Widget Aggregation" and "System-Wide Aggregation." Per-widget aggregated data is stored in the "Widget Data Store," while system-wide data is stored in the "System Performance Store." The "Widget Data Store" feeds the "Dashboard API Endpoint," which in turn populates the "Real-Time Dashboard." Similarly, the "System Performance Store" feeds the "Monitoring API Endpoint," which populates the "Admin Monitoring UI." The "Data Quality Check" acts as a crucial gatekeeper, ensuring only valid data proceeds through the pipeline, while invalid data triggers alerts for operational intervention. The use of separate data stores for widgets and system performance allows for optimized data retrieval for their respective user interfaces. The API endpoints serve as abstraction layers, decoupling the data stores from the presentation layers.
