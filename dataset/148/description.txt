## 图类型与用途
这是一个流程图，描述了 AsyncAPI 网站如何处理接收到的请求，特别是与 schema 相关的请求。该图的作用是展示请求处理的逻辑，包括判断请求是否与 schema 相关，以及如何从 GitHub 获取 schema 文件并根据响应状态进行处理。

## 图的整体布局
图采用从上到下的布局。流程从顶部的“Request”节点开始，经过一系列判断和处理步骤，最终到达底部的“Response”节点。

## 分组/子图/阶段说明
图中没有显式子图/分组，但逻辑上可以分为三个阶段：请求接收与判断、schema 获取与处理、响应生成与指标发送。

## 节点逐项说明
- **Request(Request)**：表示网站接收到的原始请求，是整个流程的起点。
- **schema-related{Is it requesting Schemas?}**：判断请求是否与 schema 相关的决策节点。
- **req_no_schemas[Let the original request go through]**：如果请求与 schema 无关，则直接让原始请求通过的节点。
- **req_schemas[Fetch from GitHub]**：如果请求与 schema 相关，则从 GitHub 获取 schema 文件的节点。
- **req_json{Was requesting a .json file?}**：判断请求的文件是否为 .json 文件的决策节点。
- **response_status{Response Status?}**：判断从 GitHub 获取 schema 后的响应状态码的决策节点。
- **response_ok[OK]**：表示响应状态码为 2xx (成功) 的节点。
- **response_cached[Not Modified]**：表示响应状态码为 304 (未修改，使用缓存) 的节点。
- **response_ko**：表示响应状态码为其他，即出现错误的节点。
- **set_headers[Set Response Content-Type header to application/schema+json]**：设置响应头，将 Content-Type 设置为 application/schema+json 的节点。
- **send_metric_success[Send success metric]**：发送成功指标的节点。
- **send_metric_error[Send error metric]**：发送错误指标的节点。
- **Response(Response)**：代表最终返回给用户的响应，是整个流程的终点。

## 连线、分支与汇聚关系
- `Request -> schema-related`：收到请求后，首先判断是否与 schema 相关。
- `schema-related -- No --> req_no_schemas`：如果与 schema 无关，则进入“Let the original request go through”节点。
- `req_no_schemas -> Response`：原始请求通过后，返回响应。
- `schema-related -- Yes --> req_schemas`：如果与 schema 相关，则进入“Fetch from GitHub”节点。
- `req_schemas -> req_json`：从 GitHub 获取 schema 后，判断是否请求的是 .json 文件。
- `req_json -- No --> Response`：如果不是 .json 文件，则直接返回响应。
- `req_json -- Yes --> response_status`：如果是 .json 文件，则判断响应状态码。
- `response_status -- 2xx --> response_ok`：如果状态码为 2xx，则进入“OK”节点。
- `response_status -- 304 --> response_cached`：如果状态码为 304，则进入“Not Modified”节点。
- `response_status -- Any other --> response_ko`：如果状态码为其他，则进入“response_ko”节点。
- `response_ok -> set_headers`：状态码为 2xx 时，设置响应头。
- `set_headers -> send_metric_success`：设置响应头后，发送成功指标。
- `response_cached -- cached:true --> send_metric_success`：状态码为 304 时，直接发送成功指标。
- `response_ko -> send_metric_error`：状态码为其他时，发送错误指标。
- `send_metric_success -- file served from raw GH --> Response`：发送成功指标后，返回响应。
- `send_metric_error -- the errored response --> Response`：发送错误指标后，返回响应。
- `send_metric_success -> Response`、`send_metric_error -> Response`、`req_no_schemas -> Response`、`req_json -- No --> Response` 形成汇聚关系。

## 仓库语境与术语解释
- **AsyncAPI**：根据 README，该仓库是 AsyncAPI 网站的源码。
- **Schema**：用于描述消息结构的定义，AsyncAPI 规范使用 Schema 来定义消息的格式和内容。
- **GitHub**：用于存储 schema 文件的远程仓库。图中可见，网站会从 GitHub 获取 schema 文件。
- **Content-Type**：HTTP 响应头，用于指定响应内容的类型。图中可见，当成功获取 schema 文件后，Content-Type 会被设置为 application/schema+json。
- **Metric**：用于衡量网站性能或用户行为的指标。图中可见，会根据请求处理的结果发送成功或失败的指标。
- **Next.js**：根据 README，AsyncAPI 网站使用 Next.js 框架构建。
- **Netlify**：根据 README，AsyncAPI 网站使用 Netlify 进行构建和部署。

## 可作为 QA Ground Truth 的高信息密度摘要
该图描述了 AsyncAPI 网站处理请求的流程。从接收“Request”开始，首先判断请求是否与 schema 相关，若无关则直接返回“Response”；若与 schema 相关，则从 GitHub 获取 schema 文件，并判断是否为 .json 文件。若是 .json 文件，则根据响应状态码分别进行处理：2xx 状态设置响应头并发送成功指标，304 状态直接发送成功指标，其他状态发送错误指标，最终都返回“Response”。其中，从 GitHub 获取 schema 和根据响应状态码进行处理是关键分支。AsyncAPI 网站使用 Next.js 和 Netlify 构建和部署。
