## 图类型与用途
这是一个分层架构图，描述了 Manager-Orchestrator 系统中不同层级之间的关系和数据流。它展示了系统如何将任务分配给不同的专家，并利用钩子函数进行验证和通知，旨在提高开发效率、保证代码质量和安全性。

## 图的整体布局
图整体采用从上到下的分层布局，分为三个主要层级：Manager-Orchestrator、Specialists 和 Hooks。信息流从顶部的 Manager 层开始，向下传递到 Specialists 层，再由 Specialists 层触发 Hooks 层。

## 分组/子图/阶段说明
图中包含三个显式子图，分别代表系统的三个层级：
- **Layer 1: Manager-Orchestrator**：包含一个节点，代表 Manager 组件，负责计划、分配任务、验证结果和进行 QA。
- **Layer 2: Specialists**：包含多个节点，代表不同的专家角色，每个专家负责特定的开发任务。
- **Layer 3: Hooks**：包含多个节点，代表不同的钩子函数，用于自动化验证、安全检查和通知等操作。

## 节点逐项说明
- **M (Manager opus 계획→분배→검증→QA)**：代表 Manager 组件，负责计划、分配任务、验证结果和进行 QA。根据 README，Manager 的角色是“计划 → 分配 → 验证 → QA → 完成”，并且“不直接写代码，只做协调”。
- **S1 (architect)**：代表架构师专家，负责架构设计。
- **S2 (frontend)**：代表前端专家，负责前端开发。
- **S3 (backend)**：代表后端专家，负责后端开发。
- **S4 (supabase)**：代表 Supabase 专家，负责 Supabase 相关开发。
- **S5 (test-writer)**：代表测试编写者，负责编写测试用例。
- **S6 (reviewer)**：代表代码审查者，负责代码审查。
- **S7 (qa-tester)**：代表 QA 测试者，负责 QA 测试。
- **S8 (bug-fixer)**：代表 Bug 修复者，负责修复 Bug。
- **H1 (auto-validate)**：代表自动验证钩子，用于自动化验证。根据 README，该 Hook 脚本会进行 TS/ESLint 自动验证，并在出错时返回 exit 2。
- **H2 (no-localStorage)**：代表禁止 localStorage 钩子，用于禁止 localStorage 的使用。根据 README，该 Hook 脚本用于阻止 localStorage 的使用，违规时返回 exit 2。
- **H3 (agent-perm)**：代表 Agent 权限钩子，用于检查 Agent 权限。
- **H4 (sql-injection)**：代表 SQL 注入钩子，用于防止 SQL 注入。根据 README，该 Hook 用于防止 Supabase MCP SQL 注入。
- **H5 (telegram)**：代表 Telegram 钩子，用于发送 Telegram 通知。根据 README，该 Hook 用于在 git push 后自动发送 Telegram 通知。
- **H6 (context-enrich)**：代表上下文丰富钩子，用于丰富上下文信息。

## 连线、分支与汇聚关系
- `M -- task() --> S1`：Manager 通过 `task()` 函数将任务分配给架构师专家。
- `M -- task() --> S2`：Manager 通过 `task()` 函数将任务分配给前端专家。
- `M -- task() --> S3`：Manager 通过 `task()` 函数将任务分配给后端专家。
- `M -- task() --> S4`：Manager 通过 `task()` 函数将任务分配给 Supabase 专家。
- `M -- task() --> S5`：Manager 通过 `task()` 函数将任务分配给测试编写者。
- `M -- task() --> S6`：Manager 通过 `task()` 函数将任务分配给代码审查者。
- `M -- task() --> S7`：Manager 通过 `task()` 函数将任务分配给 QA 测试者。
- `M -- task() --> S8`：Manager 通过 `task()` 函数将任务分配给 Bug 修复者。
- `S2 -.-> Write -.-> H1`：前端专家写入数据，触发 `auto-validate` 钩子。
- `S2 -.-> Write -.-> H2`：前端专家写入数据，触发 `no-localStorage` 钩子。
- `S3 -.-> Write -.-> H1`：后端专家写入数据，触发 `auto-validate` 钩子。
- `M -.-> Write -.-> H3`：Manager 写入数据，触发 `agent-perm` 钩子。
- `S4 -.-> MCP -.-> H4`：Supabase 专家通过 MCP 触发 `sql-injection` 钩子。
- `M -.-> git push -.-> H5`：Manager 通过 `git push` 触发 `telegram` 钩子。

## 仓库语境与术语解释
- **Manager-Orchestrator**：该系统旨在通过协调多个专家和钩子函数，自动化软件开发过程的各个阶段。
- **Specialist Agents**：指负责特定开发任务的专家角色，例如架构师、前端专家、后端专家等。
- **Hooks**：指用于自动化验证、安全检查和通知等操作的钩子函数。根据 README，Hooks 用于强制执行自动策略。
- **task()**：Manager 用于将任务分配给 Specialist Agents 的函数。
- **MCP**：图中可见，但仓库上下文未进一步说明。
- **opus**：图中 Manager 节点的标签包含 "opus"，README 中 "Phase별 상세 정보" 表格显示 "计划 수립" 阶段的 "执行主体" 是 "Manager (直接)"，"模型" 是 "opus"。
- **sonnet**：README 中 "Phase별 상세 정보" 表格显示，除了 "计划 수립" 和 "완료" 阶段，其他阶段的 "模型" 都是 "sonnet"。

## 可作为 QA Ground Truth 的高信息密度摘要
该图展示了 Manager-Orchestrator 系统的三层架构。Manager 作为核心组件，通过 `task()` 函数将任务分配给不同的专家（architect, frontend, backend 等），专家在完成任务时会触发相应的钩子函数（auto-validate, no-localStorage, sql-injection 等）进行验证和通知。Manager 通过 `git push` 触发 `telegram` 钩子发送通知。该架构旨在通过中心化的 Manager 组件协调多个专家，并利用钩子函数保证代码质量和安全性。其中，Hooks 用于强制执行自动策略，确保开发过程符合规范。
