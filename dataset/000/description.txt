## Diagram Type & Purpose

It depicts the steps involved in analyzing code structure, creating embeddings, selecting a model provider for documentation generation, and organizing the output. The diagram serves as a high-level overview of the entire workflow.

## Overall Layout
The diagram's primary direction is top-to-bottom (TD). The start node is "User inputs GitHub/GitLab/Bitbucket repo", and the end node is "Interactive DeepWiki".

No explicit subgraphs; logically divided into 5 stages:

## High-Density QA Ground Truth Summary
The process begins with the user providing a repository URL from GitHub, GitLab, or Bitbucket. A check determines if the repository is private; if so, the user must provide an access token. Regardless, the repository is then cloned. Next, the code structure is analyzed, and code embeddings are created, capturing the semantic meaning of the code. A model provider is then selected from options like Google Gemini, OpenAI, OpenRouter, Local Ollama, or Azure. Based on the chosen provider, documentation is generated. Simultaneously, visual diagrams are created from the code embeddings. Both the generated documentation and visual diagrams are then organized into a wiki format. Finally, the wiki is presented as an interactive DeepWiki. The code embeddings are crucial for both documentation generation and visual diagram creation, allowing the system to understand the code's semantic relationships. The choice of model provider impacts the style and quality of the generated documentation.
