## 图类型与用途
这是一个流程图，展示了 PatchMon 系统的整体架构和数据流。它描述了用户如何通过浏览器与系统交互，以及系统内部组件如何协同工作，是理解系统架构的概览图。

## 图的整体布局
图采用从左到右的布局，展示了从用户界面到后端服务和数据库的数据流。整体层次结构可以看作是前端、后端和数据层。

## 分组/子图/阶段说明
图中没有显式子图/分组，但逻辑上可分为用户交互层、反向代理层、后端服务层和数据存储层四个阶段。

## 节点逐项说明
- **A [Browser / Admin UI]**：用户的浏览器或管理员用户界面，是用户与 PatchMon 系统交互的入口。
- **B [nginx]**：Nginx Web 服务器，作为反向代理和负载均衡器，接收来自浏览器/Admin UI的HTTPS请求，并将其转发到后端服务。
- **C [Backend - Node / Express]**：后端服务，使用 Node.js 和 Express 框架构建，处理来自 nginx 的 HTTP 请求，并与数据库和缓存进行交互。它是系统的核心逻辑处理单元。
- **D [(PostgreSQL)]**：PostgreSQL 数据库，用于存储 PatchMon 系统的数据，例如服务器信息、补丁状态等。
- **R [(Redis)]**：Redis 缓存，用于缓存数据，提高系统性能。
- **E [Agents on your servers]**：部署在用户服务器上的代理程序，负责收集服务器信息，并将信息通过 HTTPS 发送到后端服务。这些 Agent 通过 outbound-only 的方式连接 PatchMon 服务，无需在被监控主机上开放任何入站端口，参见 README。

## 连线、分支与汇聚关系
- `A -> B`：用户通过 Browser / Admin UI 发起 HTTPS 请求到 nginx。
- `B -> C`：nginx 将 HTTP 请求转发到 Backend - Node / Express。
- `C -> D`：Backend 通过 TCP 连接与 PostgreSQL 数据库进行数据交互。
- `C -> R`：Backend 通过 TCP 连接与 Redis 缓存进行数据交互。
- `E -> C`：Agents on your servers 通过 HTTPS 连接将服务器信息发送到 Backend，形成汇聚关系。

## 仓库语境与术语解释
- **PatchMon**：一个企业级的 Linux 补丁监控和服务器管理平台，参见 README。
- **nginx**：用作反向代理和负载均衡器，配置文件模板位于 `docker/nginx.conf.template`。
- **Backend - Node / Express**：后端服务使用 Node.js 和 Express 框架构建，代码位于 `backend/src/server.js`。
- **PostgreSQL**：用于存储 PatchMon 系统的数据，数据库连接配置位于 `backend/src/config/prisma.js`。
- **Redis**：用于缓存数据，提高系统性能，相关配置在 `docker/docker-compose.yml` 中。
- **Agents on your servers**：部署在用户服务器上的代理程序，其源代码位于 `agent-source-code/` 目录下，主程序入口是 `agent-source-code/cmd/patchmon-agent/main.go`。

## 可作为 QA Ground Truth 的高信息密度摘要
这张图展示了 PatchMon 系统的整体架构。用户通过浏览器或 Admin UI 发起 HTTPS 请求，经过 nginx 反向代理后到达后端 Node/Express 服务。后端服务与 PostgreSQL 数据库和 Redis 缓存进行数据交互。同时，部署在用户服务器上的 Agents 通过 HTTPS 连接将服务器信息发送到后端服务。整个架构体现了“用户界面 -> 反向代理 -> 后端服务 -> 数据存储”的数据流，其中 nginx 作为反向代理和负载均衡器，Agents 作为数据采集端是两个关键组成部分。
