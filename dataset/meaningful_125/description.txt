## Edges, Branches & Convergence
- `A --> B`: Initial load of raw customer transaction data into the landing zone.
- `B --> C`: Data flows from the landing zone to schema validation.
- `C -- Yes --> D`: If schema validation passes, data moves to the staging zone.
- `C -- No --> E`: If schema validation fails, data moves to the quarantine zone.
- `E --> F`: An alert is sent to the data quality team when data is quarantined.
- `D --> G`: Data flows from the staging zone to data quality checks.
- `G -- Pass --> H`: If data quality checks pass, data is cleansed using a PySpark job.
- `G -- Fail --> I`: If data quality checks fail, an exception is logged.
- `I --> F`: An alert is sent to the data quality team when data quality checks fail.
- `H --> J`: Data is transformed through deduplication and enrichment.
- `J --> K`: Transformed data is stored in Parquet format in the hot tier S3 bucket.
- `K --> L`: Data from the hot tier is used to populate a real-time dashboard.
- `K --> M`: Data from the hot tier is rolled up on a schedule to create aggregations.
- `M --> N`: Summarized data is stored in Parquet format in the warm tier S3 bucket.
- `N --> O`: Data from the warm tier is used for interactive BI tools.
- `N --> P`: Data from the warm tier is periodically archived and converted to ORC format in the cold tier S3 bucket.
- `P --> Q`: Data from the cold tier is used for historical data analysis.
- `Q --> R`: Historical data analysis results are used for reporting, audit, and compliance.
- `P --> S`: Data from the cold tier is moved to Glacier for long-term archival on a monthly basis.
- `S --> T`: Data in Glacier is used for disaster recovery and compliance.

## Repository Context & Terminology
- **S3 Bucket**: Scalable storage in the cloud, used for storing data at various stages.
- **PySpark**: Python API for Apache Spark, a distributed computing framework used for data processing.
- **Parquet**: Columnar storage format optimized for analytics.
- **ORC**: Optimized Row Columnar, another columnar storage format optimized for Hive.
- **Presto/Athena**: Distributed SQL query engines for querying large datasets.
- **Tableau/Looker**: Business intelligence tools for data visualization and analysis.
- **EMR/Hive**: Elastic MapReduce and Hive, used for big data processing and querying.
- **Glacier**: Low-cost storage service for long-term archival.

## High-Density QA Ground Truth Summary
The data pipeline begins with raw customer transaction data ingested from a data source into the Landing Zone, an S3 bucket designated as `/raw`. An initial load process moves the data to the next stage, where a schema validation check is performed. If the schema is valid (`Yes` branch), the data proceeds to the Staging Zone, another S3 bucket at `/staging`. If the schema is invalid (`No` branch), the data is quarantined in an S3 bucket at `/quarantine`, and an alert is sent to the data quality team. Data in the Staging Zone undergoes data quality checks. Passing these checks (`Pass` branch) leads to data cleansing via a PySpark job, followed by transformation involving deduplication and enrichment. Failing the quality checks (`Fail` branch) triggers exception logging and an alert to the data quality team. Transformed data is then stored in Parquet format in the Hot Tier S3 bucket at `/hot`, optimized for real-time analytics, and used in a Real-Time Dashboard powered by Presto/Athena. A scheduled roll-up process moves data from the Hot Tier to the Warm Tier, where it is summarized using Spark aggregation and stored in an Optimized Parquet S3 bucket at `/warm`. This data is used with interactive BI tools like Tableau/Looker. Periodically, data from the Warm Tier is archived and converted to ORC format in the Cold Tier S3 bucket at `/cold`, used for historical data analysis with EMR/Hive, and ultimately for reporting, audit, and compliance. Monthly, data from the Cold Tier is moved to Glacier for long-term archival, supporting disaster recovery and compliance needs.
