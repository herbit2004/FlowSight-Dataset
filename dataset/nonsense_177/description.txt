## 图类型与用途
该图是一个流程图，描述了处理用户请求的流程，涉及数据库、缓存、消息队列等组件。该流程图展示了数据是否存在、缓存是否命中、支付是否成功等多个判断分支。

## 图的整体布局
该图的布局是从上到下。流程从“用户请求”开始，最终到达“用户响应”。整体流程包含多个判断分支和循环。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可分为以下阶段：
1. 请求与数据校验阶段：用户请求，数据库数据校验。
2. 缓存处理阶段：读取缓存，判断缓存是否命中。
3. 数据更新阶段：更新数据库，消息队列处理。
4. 支付处理阶段：判断支付是否成功，重试支付。
5. 响应阶段：生成订单，用户响应。

## 节点逐项说明
- **A**：用户请求的起始节点。
- **B**：数据库节点，用于存储和检索数据。
- **C**：判断节点，判断数据库中数据是否存在。
- **D**：删除缓存节点，当数据库中数据存在时执行。
- **E**：读缓存节点，当数据库中数据不存在时执行。
- **F**：判断节点，判断缓存是否命中。
- **G**：API 网关节点，当缓存命中时执行。
- **H**：更新数据库节点，当缓存未命中时执行。
- **I**：消息队列节点，用于异步处理消息。
- **J**：判断节点，判断支付是否成功。
- **K**：生成订单节点，当支付成功时执行。
- **L**：重试支付节点，当支付不成功时执行。
- **M**：用户响应节点，流程的结束节点。

## 连线、分支与汇聚关系
- A -> B：用户请求发送到数据库。
- B -> C：数据库返回数据存在状态。
- C -- Yes --> D：如果数据存在，则删除缓存。
- C -- No --> E：如果数据不存在，则读取缓存。
- E -> F：读取缓存后，判断缓存是否命中。
- F -- Yes --> G：如果缓存命中，则通过 API 网关。
- F -- No --> H：如果缓存未命中，则更新数据库。
- H -> I：更新数据库后，发送消息到消息队列。
- I -> J：消息队列处理支付请求，判断支付是否成功。
- J -- Yes --> K：如果支付成功，则生成订单。
- J -- No --> L：如果支付不成功，则重试支付。
- L -> I：重试支付请求发送到消息队列。
- G -> A：API 网关处理后，返回用户请求。
- K -> M：生成订单后，返回用户响应。
- D -> A：删除缓存后，返回用户请求。

## 仓库语境与术语解释
- **用户请求**：用户发起的对系统的操作请求。
- **数据库**：用于存储和管理数据的系统。
- **缓存**：用于临时存储数据，提高访问速度。
- **API 网关**：系统的入口，负责请求路由、鉴权等功能。
- **消息队列**：用于异步处理消息的中间件。
- **支付**：用户为购买商品或服务进行的付款操作。
- **订单**：用户购买商品或服务的记录。

## 可作为 QA Ground Truth 的高信息密度摘要
用户请求首先到达数据库，判断数据是否存在。如果存在，则删除缓存并返回用户请求；如果不存在，则读取缓存，判断缓存是否命中。如果缓存命中，则通过 API 网关返回用户请求；如果缓存未命中，则更新数据库，并将支付请求发送到消息队列。消息队列判断支付是否成功，如果成功则生成订单并返回用户响应，否则重试支付，直到支付成功。
