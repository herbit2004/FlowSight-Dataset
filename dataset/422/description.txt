## 图类型与用途
这是一个流程图，描述了 SpecMaster 系统中从需求边界确认到 Spec 规范制定的详细流程。该图用于展示 SpecMaster 如何将模糊需求转化为可执行的规范，是规范驱动开发（SDD）流程中的核心部分。

## 图的整体布局
图采用从上到下的布局。顶部是流程的起始阶段“S01 需求边界确认”，向下依次展开为子任务和后续阶段，最终连接到质量检查和版本管理。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可分为三个阶段：需求边界确认（S01）、Spec 规范制定（S02）以及质量检查与版本管理。

## 节点逐项说明
- **A (S01 需求边界确认)**：流程的起始阶段，负责明确项目的范围和边界。
- **A1 (S01.1 项目基础信息收集)**：收集项目的基本信息，为后续的需求分析和规范制定打下基础。
- **A2 (S01.2 模糊需求识别与标记)**：识别并标记用户提出的模糊需求，以便后续进行澄清和细化。
- **B (S02 Spec 规范制定)**：核心阶段，将模糊的需求转化为详细的、可执行的规范。
- **B1 (S02.1 创建 Spec 目录结构)**：建立规范文档的目录结构，为后续的规范编写提供框架。
- **B2 (S02.2 需求总览文档编写)**：编写需求总览文档，对项目需求进行整体性的描述。
- **B3 (S02.3 功能需求详细定义)**：详细定义每个功能的需求，包括输入、输出、处理逻辑等。
- **B4 (S02.4 非功能需求定义)**：定义非功能需求，如性能、安全性、可维护性等。
- **B5 (S02.5 边界与异常处理)**：定义系统的边界条件和异常处理机制，确保系统的健壮性。
- **B6 (S02.6 验收标准制定)**：制定验收标准，用于验证规范的正确性和完整性。
- **B7 (S02.7 需求澄清与迭代)**：对需求进行澄清，并根据反馈进行迭代，确保需求的准确性。
- **QC1 (QC01 Spec 质量检查)**：对 Spec 规范进行质量检查，确保规范的质量符合要求。
- **VM (VM01 版本信息管理)**：对 Spec 规范进行版本管理，记录每次修改的内容和版本号。

## 连线、分支与汇聚关系
- `A -> B`：从需求边界确认阶段进入 Spec 规范制定阶段。
- `A -> A1`：需求边界确认阶段包含项目基础信息收集子任务。
- `A -> A2`：需求边界确认阶段包含模糊需求识别与标记子任务。
- `B -> B1`：Spec 规范制定阶段包含创建 Spec 目录结构子任务。
- `B -> B2`：Spec 规范制定阶段包含需求总览文档编写子任务。
- `B -> B3`：Spec 规范制定阶段包含功能需求详细定义子任务。
- `B -> B4`：Spec 规范制定阶段包含非功能需求定义子任务。
- `B -> B5`：Spec 规范制定阶段包含边界与异常处理子任务。
- `B -> B6`：Spec 规范制定阶段包含验收标准制定子任务。
- `B -> B7`：Spec 规范制定阶段包含需求澄清与迭代子任务。
- `B7 -> QC1`：需求澄清与迭代后进行 Spec 质量检查。
- `B1 -> VM`：创建 Spec 目录结构后进行版本信息管理。

## 仓库语境与术语解释
- **SpecMaster**：一个专业的规范驱动开发（SDD）智能助手，旨在引导用户按照SDD核心原则，完成从"模糊需求→Spec规范→技术方案"的全流程落地，确保从"意图定义"到"技术实现"无断层、可追溯。
- **SDD (Specification-Driven Development)**：规范驱动开发，一种以规范为核心的开发方法，强调规范的可执行性和可追溯性。
- **Spec 规范**：聚焦意图，无技术细节的需求规范，是 SpecMaster 的核心输出。
- **TechPlan**：技术方案制定智能助手，负责将 Spec 规范转化为技术实现方案，详细流程请参考 `TechPlanSystemPrompts.md` 文件。
- **版本信息管理**：所有 Spec 和技术方案文档都必须包含版本信息，遵循语义化版本规范。
- **WHO-GIVEN-WHEN-THEN-SHALL 框架**：用于编写用户故事的标准格式，确保需求描述的完整性和可测试性，详情见 `SpecMasterSystemPrompts.md`。

## 可作为 QA Ground Truth 的高信息密度摘要
该图描述了 SpecMaster 系统中从需求边界确认到 Spec 规范制定的核心流程。流程从“S01 需求边界确认”开始，包括项目基础信息收集和模糊需求识别与标记两个子任务，然后进入“S02 Spec 规范制定”阶段，包含创建 Spec 目录结构、编写需求总览文档等多个子任务，最终进行 Spec 质量检查和版本信息管理。该流程体现了规范驱动开发（SDD）的核心理念，确保从模糊需求到可执行规范的转化。
