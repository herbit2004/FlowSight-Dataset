## 图类型与用途
该图是流程图，描述了一个工作流引擎和一个通知服务之间的交互流程。该流程包括申请提交、审批、风险评估、报告生成、数据同步、状态更新等环节，以及相应的通知机制。该图展示了申请处理的完整生命周期。

## 图的整体布局
该图采用从上到下的布局。整体分为两个子图：工作流引擎和通知服务。工作流引擎是主流程，从提交申请开始，到结束（完成或驳回）为止；通知服务则贯穿整个流程，在多个关键节点发送通知。

## 分组/子图/阶段说明
图中包含两个子图：
- **工作流引擎**：负责处理申请的整个流程，包括提交、审批、风险评估、报告生成、数据同步和状态更新。
- **通知服务**：负责发送通知，包括接收方是否收到通知的重试机制。

## 节点逐项说明
- **A (提交申请)**：流程的起始节点，表示用户提交申请。
- **B (审批人)**：负责审批申请的节点，根据审批结果决定后续流程。
- **C (风险评估)**：对申请进行风险评估的节点，根据风险等级决定后续流程。
- **D (自动批准)**：当风险评估低于阈值时，自动批准申请的节点。
- **E (高级审批)**：当风险评估高于阈值时，需要高级审批的节点。
- **F (生成报告)**：生成申请处理报告的节点。
- **G (同步数据)**：将申请处理数据同步到其他系统的节点。
- **H (更新状态)**：更新申请状态的节点。
- **I (结束: 驳回/完成)**：流程的结束节点，表示申请被驳回或完成。
- **J (发送通知)**：发送通知的节点。
- **K (接收方)**：接收通知的节点。
- **L (已读)**：表示接收方已读通知。
- **M (重试通知)**：当接收方未收到通知时，重试发送通知的节点。

## 连线、分支与汇聚关系
- A -> B：提交申请后，进入审批环节。
- B -- 同意 --> C：审批人同意申请，进入风险评估环节。
- B -- 拒绝 --> I：审批人拒绝申请，流程结束（驳回）。
- C -- 低于阈值 --> D：风险评估低于阈值，进入自动批准环节。
- C -- 高于阈值 --> E：风险评估高于阈值，进入高级审批环节。
- D -> F：自动批准后，生成报告。
- E -- 同意 --> F：高级审批同意后，生成报告。
- E -- 拒绝 --> I：高级审批拒绝后，流程结束（驳回）。
- F -> G：生成报告后，同步数据。
- G -> H：同步数据后，更新状态。
- H -> I：更新状态后，流程结束（完成）。
- J -> K：发送通知后，等待接收方接收。
- K -- 收到 --> L：接收方收到通知，标记为已读。
- K -- 未收到 --> M：接收方未收到通知，进入重试通知环节。
- M -> J：重试通知，重新发送通知。
- A -> J：提交申请后，发送通知。
- F -> J：生成报告后，发送通知。
- I -> J：流程结束后（无论完成或驳回），发送通知。

## 仓库语境与术语解释
本图为合成数据，无真实仓库。
- **工作流引擎**：负责自动化执行一系列任务的系统，通常用于管理业务流程。
- **风险评估**：评估潜在风险的过程，用于确定风险等级并采取相应的措施。
- **高级审批**：需要更高权限人员进行的审批，通常用于处理高风险或重要事项。
- **同步数据**：将数据从一个系统复制到另一个系统，以保持数据一致性。
- **通知服务**：负责发送通知的系统，通常用于告知用户或系统管理员重要事件或状态变更。
- **阈值**：一个预先设定的数值，用于判断某个指标是否达到某个标准。
- **重试通知**：当通知发送失败时，重新发送通知的机制。

## 可作为 QA Ground Truth 的高信息密度摘要
申请提交后，进入审批环节。如果审批同意，则进行风险评估；否则，流程结束并驳回申请。风险评估结果低于阈值则自动批准，高于阈值则需要高级审批。高级审批也可能同意或拒绝，拒绝则流程结束并驳回申请。批准后，生成报告，同步数据，更新状态，流程结束并完成。在提交申请、生成报告以及流程结束时，都会发送通知给相关人员，如果接收方未收到通知，系统会重试发送。
