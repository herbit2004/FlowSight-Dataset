## Diagram Type & Purpose
This is a flowchart diagram illustrating the operation of a distributed cache system. It depicts the flow of a client request, the cache lookup process, interaction with the origin server, cache updates, and invalidation mechanisms. The diagram serves as a visual representation of the system's architecture and logic, aiding in understanding the data flow and component interactions.

## Overall Layout
The diagram's primary direction is top-down (TD). It illustrates a hierarchical flow, starting with a client request and ending with the client receiving a value or an invalidation confirmation being sent to the origin server. The start node is "Client Request" and the end node is "Client Application".

## Repository Context & Terminology
- **Distributed Cache**: A system that stores copies of data at various network locations to improve access times and reduce the load on origin servers.
- **Cache Hit**: When the requested data is found in the cache.
- **Cache Miss**: When the requested data is not found in the cache.
- **Origin Server**: The primary source of data.
- **Invalidation Event**: A notification that data in the cache is no longer valid and needs to be updated.
- **Least Recently Used (LRU)**: A cache eviction policy that removes the least recently accessed items to make space for new data.
- **Timestamp**: A record of when an event occurred, used for tracking invalidation and access times.

## High-Density QA Ground Truth Summary
The distributed cache system begins with a "Client Request," which immediately leads to a "Cache Hit?" decision. If the data is present (Cache Hit? -- Yes), the system "Return Cached Value" directly to the "Client Receives Value," ultimately reaching the "Client Application." If the data is not in the cache (Cache Hit? -- No), the system "Request Origin Server." The "Origin Server Processing" then determines if "Data Changed?" If yes, a "Publish Invalidation Event" is triggered, sending a signal to the "Invalidation Service" to "Receive Invalidation Event." The invalidation service checks "Local Cache Entry Exists?" and either invalidates the entry and updates the timestamp, or takes no action if the entry doesn't exist, before sending an "Acknowledge Invalidation Event" back to the "Origin Server" as "Invalidation Confirmation to Origin Server." If the origin server determines that the data has not changed, it will "Return Value Directly" to the "Return Value to Cache & Client" node. The "Return Value to Cache & Client" node updates the cache, checking if the "Cache Size Limit Reached?" If so, the system "Evict Least Recently Used Entry" before storing the new value. Finally, the system "Return Value to Client" and the "Client Receives Value" before reaching the "Client Application." The cache invalidation mechanism ensures data consistency across the distributed cache nodes.
