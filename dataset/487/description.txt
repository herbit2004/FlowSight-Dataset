## 图类型与用途
这是一个流程图，描述了基于行为驱动开发（BDD）的软件开发流程，从用户行为到最终代码合并的自动化过程。该图在仓库中用于展示 Behavioral 开发方法，是 README.md 中 Development Methodologies 的一部分。

## 图的整体布局
图采用从左到右的布局。流程从左侧的“User Behavior”开始，经过一系列转换和处理，最终到达右侧的“Merge”。

## 分组/子图/阶段说明
图中没有显式子图，但逻辑上可以分为以下几个阶段：需求分析与规范化、任务分解、智能体编排、代码提交与合并。

## 节点逐项说明
- **User Behavior**：表示用户的行为或需求，是整个流程的起点。
- **BDD Spec + Gherkin**：表示行为驱动开发（BDD）规范和 Gherkin 语法，用于将用户行为转化为可执行的规范。
- **Epic + Sub-Issues**：表示 Epic（史诗级任务）和子任务，用于将大型用户故事分解为更小的、可管理的子任务。
- **Agent Orchestration**：表示智能体编排，利用多个 AI 智能体协同工作来完成子任务。
- **Pull Request**：表示拉取请求，智能体编排的结果会被提交为一个拉取请求，等待审核。
- **Merge**：表示代码合并，经过审核后，拉取请求会被合并到主代码库中。

## 连线、分支与汇聚关系
- `User Behavior -> BDD Spec + Gherkin`：用户行为通过 `/user-story` 转化为 BDD 规范和 Gherkin 语法。
- `BDD Spec + Gherkin -> Epic + Sub-Issues`：BDD 规范通过 `/issue` 分解为 Epic 和子任务。
- `Epic + Sub-Issues -> Agent Orchestration`：子任务通过 `/task` 被分配给智能体进行编排执行。
- `Agent Orchestration -> Pull Request`：智能体编排的结果通过 `/pr` 提交为一个拉取请求。
- `Pull Request -> Merge`：拉取请求经过 `Review` 审核后被合并到主代码库。

## 仓库语境与术语解释
- **BDD (Behavior-Driven Development)**：行为驱动开发，一种软件开发方法，强调从用户行为出发，使用 Gherkin 语法编写可执行的规范。
- **Gherkin**：一种用于描述软件行为的语言，通常用于编写自动化测试。
- **Epic**：一个大型的用户故事，通常需要分解为更小的、可管理的子任务。
- **Agent Orchestration**：利用多个 AI 智能体协同工作来完成子任务，该仓库通过 `commands/task.md` 实现任务分解和智能体分配。
- **Pull Request**：一种代码提交方式，用于将代码变更提交到主代码库进行审核。`commands/pr.md` 用于创建 pull request。

## 可作为 QA Ground Truth 的高信息密度摘要
该图描述了从用户行为开始，通过 BDD 规范和 Gherkin 语法转化为可执行规范，再分解为 Epic 和子任务，然后通过智能体编排自动完成子任务，最终提交 Pull Request 并合并的完整流程。其中，用户行为到 BDD 规范的转换、子任务分解和智能体编排是关键环节，最终通过代码审核流程确保代码质量。该流程对应 README.md 中描述的 Behavioral 开发方法。
